# 추론 서비스 (Python)

- 담당: 
- 기술: Python, FastAPI, YOLO
- 포트: 8001

스테이션(C#)이 정렬된 보드 이미지를 보내면, **어느 핀홀에 어떤 부품이 꽂혀 있는지**를
반환한다. 장착 상태가 맞는지 틀린지 "판정"(PASS/FAIL)은 하지 않는다 — 그건 스테이션의 몫이다.
모델 가중치와 데이터셋은 Git에 올리지 않는다.

API 계약(요청/응답 형식)은 [docs/api-contract.md](../docs/api-contract.md) 참고.

## 처리 흐름

이미지 한 장이 들어와서 `{pinhole, class, confidence}` 목록이 나가기까지, 4단계를 거친다.

```mermaid
flowchart TD
    IMG[이미지 JPEG] --> DECODE[0. 디코딩 + 회전(90도 + 미세 보정) + 크롭<br/>roi.crop_to_roi<br/>가로: 레일 선 검출 + 중앙 단위 선택<br/>세로: "10"·"30" 라벨 OCR로 실측]
    DECODE --> DETECT

    subgraph S1["1. 홀 검출 (완성)"]
        DETECT[board_detect.find_pinhole_pixels<br/>홀 blob 검출 → 열은 간격 기반 그룹핑(실측값),<br/>행은 모든 열을 합쳐 y=b0+b1·행번호+b2·x<br/>평면 하나로 최소제곱 계산 (이미지 변형 없음)]
    end

    DETECT --> HOLES[282개 Hole 객체 생성<br/>board.all_holes_from_image]
    DECODE --> YOLO

    subgraph S2["2. 부품 탐지 (TODO)"]
        YOLO[크롭된 이미지로 YOLO 탐지<br/>픽셀 사각형 + 종류·신뢰도]
    end

    HOLES --> MATCH[3. 홀-박스 대조<br/>board.match_holes_to_boxes<br/>홀 위치가 박스 안에 들어가면<br/>그 홀 = 가려짐 장착됨]
    YOLO --> MATCH
    MATCH --> OUT[가려진 홀만 추려서<br/>parts 배열로 응답]
```

**왜 이런 순서인가**
- 카메라가 눕혀서 찍기 때문에, 크롭 전에 먼저 왼쪽(반시계) 90도로 돌린다 (`roi.ROTATE`). 근데 90도 회전은 큰 방향만 맞출 뿐 완벽한 수직을 보장하지 않는다 — 카메라 장착 각도가 정확히 90도가 아니면 레일 선이 아주 살짝 기울어져 있을 수 있다(실측: 사진마다 -1.0~+1.3도 정도). 그래서 레일 선의 실제 기울기를 재서(`rail_detect.measure_tilt_angle`) 한 번 더 미세하게 돌린다(deskew). 사진 전체가 아니라 **선택된 단위의 두 경계선만**으로 각도를 재는데, 실측해보니 사진 안에서도 위치(x)에 따라 기울기가 조금씩 달랐기 때문이다(렌즈 왜곡/원근 영향으로 보임) — 우리가 실제로 쓸 단위 기준으로만 재야 그 단위 안에서 정확하다.
- 처음엔 "카메라·지그가 고정이니 세로 범위(`roi.Y_RANGE`)도 고정값으로 충분하다"고 가정했는데, **실측(`board2.jpg`)으로 틀렸다는 게 확인됐다** — 카메라 위치·줌이 사진마다 미묘하게 달라서, 같은 고정 픽셀 범위가 어떤 사진에서는 행 A~U를 다 담고 어떤 사진에서는 마지막 행(U)을 잘라버렸다. 그래서 지금은 실크스크린에 인쇄된 행 번호 라벨(10,15,20,25,30)을 **OCR(Tesseract)로 읽어서** 그 간격으로 세로 범위를 매번 계산한다 (`label_detect.py`). `roi.Y_RANGE`는 이제 최종값이 아니라 "대략 이 근처"라는 탐색 시작점일 뿐이다. 라벨 5개를 다 찾을 필요는 없다 — 실측(`board3.jpg`)해보니 같은 보드에서도 라벨마다 폰트가 달라서("30"만 필기체 스타일) 하나만 OCR이 실패하는 경우가 있었는데, 2개 이상 찾히면 선형회귀로, 1개만 찾혀도 기본 피치로 나머지를 추정하도록 만들어서 해결했다.
- 가로(열) 방향도 사진마다 레일 선 위치가 40px 넘게 달라졌다 (카메라가 살짝씩 밀림). 그래서 가로도 고정 숫자로 자르지 않고, **매번 빨강/파랑 전원 레일 선을 색으로 찾아서**(`rail_detect.py`) 후보 단위들을 찾는다. 딥러닝이 아니라 HSV 색상 임계값 기반의 전통적 머신비전이다.
- 프레임 안에 이런 "레일-단자부-단자부-레일" 단위가 여러 개 있으면(테스트 사진처럼 보드가 여러 개 같이 찍힌 경우), **프레임 중앙에 가장 가까운 것을 고른다** (`find_center_unit_x_range`) — 카메라·지그가 고정돼 있으면 검사 대상 보드는 항상 중앙 부근에 놓인다는 가정. "부품이 많아 보이는 곳"(edge 밀도, `find_populated_unit_x_range`)보다 부품 개수·조명에 안 흔들려서 더 안정적이다. 실제 검사 라인처럼 보드가 하나뿐이면 후보도 하나뿐이라 결과는 똑같다.
- 크롭 후에도 보드 위치·기울기·크기가 더 미세하게(픽셀 단위로) 조금씩 다르다. 그래서 핀홀 픽셀 위치를 고정값으로 하드코딩할 수 없고, **크롭된 이미지마다 다시 계산**해야 한다.
- 처음엔 네 모서리 핀홀 픽셀 좌표만 찾아서 `calibration.py`의 호모그래피로 나머지 278개 위치를 선형보간하려 했는데, **실측해보니 부정확했다** — 이 브레드보드는 열 6~7 사이에 단자부 채널(물리적으로 넓은 갭)이 있어서 열 간격이 균등하지 않은데, 모서리 4개짜리 단일 호모그래피는 균등한 간격을 가정하기 때문이다. `calibration.py`는 이 한계 때문에 레거시로 남아있다 (calibration.py 문서 참고).
- 그다음엔 네 모서리로 원근 변환(perspective warp)해서 기울기(회전)만 이미지를 평면처럼 편 다음 검출하는 방법도 시도했는데, 부품이 많은 사진(`board1.jpg`)에서 실측해보니 **오히려 왜곡이 더 커졌다**. 그래서 지금 `board_detect.py`는 **이미지를 아예 변형하지 않는다.**
- 행 위치를 구할 때 두 가지 버그를 실측으로 잡았다. ① 레일 열(0,1,12,13)은 E/K/Q 행이 빠져서 18칸인데, 이걸 그냥 "17칸 균등 간격"으로 나누면 틀린다 — D-F, J-L, P-R 사이는 (건너뛴 자리만큼) 물리적으로 2칸 너비라서 진짜 물리적 간격은 20칸이다. `pinhole_grid.ROWS`(A~U, 21개) 안에서의 실제 인덱스를 기준으로 계산하도록 고쳤다. ② 처음엔 **열마다 따로** 그 열 자신의 첫 홀~마지막 홀 사이를 선형보간했는데, "같은 알파벳(행)의 핀홀은 항상 일직선이어야 한다"는 물리적 제약을 이 방식이 구조적으로 보장하지 못했다 — 열마다 독립적으로 계산하다 보니 같은 행이라도 열마다 y값이 살짝 어긋날 수 있었다 (`board1.jpg`에서 실측 확인됨). 그래서 지금은 **모든 열의 모든 홀을 한꺼번에** 써서 `y = b0 + b1*행번호 + b2*x` 평면 하나를 최소제곱으로 피팅한다 — 평면 하나로 모든 위치를 계산하므로 같은 행번호는 정의상 항상 일직선이 된다. (WORKLOG.md 참고) 세 사진 모두 레일 열까지 포함해 픽셀 단위로 정확히 맞는 것까지 확인됨.
- "박스 중심과 가장 가까운 핀홀 하나"를 고르는 대신, 반대로 "핀홀마다 어떤 박스 안에 들어가는지"를 본다. 이러면 저항처럼 다리(핀) 두 개짜리 부품이 핀홀 두 개에 걸쳐 있어도 둘 다 자연스럽게 잡힌다.

## 파일 구성

| 파일 | 역할 | 상태 |
|---|---|---|
| [app/main.py](app/main.py) | FastAPI 앱. `/health`, `/infer` 엔드포인트 | 뼈대 완성, TODO 1곳 남음 |
| [app/roi.py](app/roi.py) | 원본 이미지를 회전(왼쪽 90도 + 레일 선 기울기로 미세 보정) 후, 가로는 레일 선 검출 + 중앙 단위 선택, 세로는 행 번호 라벨 OCR로 크롭 | 완성 (실제 사진 4장으로 검증됨) |

| [app/label_detect.py](app/label_detect.py) | 행 번호 라벨(10,15,20,25,30)을 OCR(Tesseract)로 찾아 세로 크롭 범위 계산. 찾은 라벨 개수에 따라 선형회귀/외삽으로 대응 | 완성 |
| [app/pinhole_grid.py](app/pinhole_grid.py) | 핀홀 282개의 그리드 정의(행 A~U, 열 0~13)와 라벨 변환 | 완성 |
| [app/board_detect.py](app/board_detect.py) | 크롭된 이미지에서 홀을 직접 검출 → 열은 간격 기반 그룹핑, 행은 모든 열을 합친 평면(y=b0+b1·행번호+b2·x) 최소제곱 피팅 → 282개 핀홀의 실제 픽셀 위치 계산 (이미지 변형 없음) | 완성 (실제 사진 4장으로 검증됨) |
| [app/calibration.py](app/calibration.py) | (레거시) 네 모서리 핀홀 픽셀 좌표 → 호모그래피 → 픽셀 ↔ 그리드 좌표 변환. 열 간격 비균등 문제로 부정확해서 board_detect.py로 대체됨 | 레거시 |
| [app/board.py](app/board.py) | 핀홀 282개를 이미지 속 위치·장착 여부와 함께 구조화, YOLO 박스와 대조 | 완성 |

> **환경 준비**: `pytesseract`는 pip 패키지일 뿐이고, 실제 OCR 엔진인 **Tesseract 실행 파일이 별도로 설치**돼 있어야 한다. `conda install -c conda-forge tesseract` (지금 개발 환경 `pcb-aoi`엔 이미 설치됨) 또는 Windows용 설치 프로그램을 쓴다. `label_detect.py`가 conda 환경 경로 기준으로 실행파일·언어 데이터 경로를 자동으로 잡아준다.
>
> `roi.Y_RANGE`는 이제 최종 세로 크롭값이 아니라 "대략 이 근처"라는 탐색 시작점일 뿐이다 — 가로는 `rail_detect.py`가, 세로는 `label_detect.py`(OCR)가 매번 다시 찾으므로 카메라가 조금 움직이거나 줌이 달라져도 괜찮다. 두 검출이 전부 실패하는 극단적인 경우에만 각각의 예비 고정값으로 대체된다.
>
> 참고: 테스트 사진처럼 책상에 브레드보드가 여러 개 나란히 놓여 있어도, `crop_to_roi()`는 그중 프레임 중앙에 가장 가까운 것을 스스로 골라낸다 (`find_center_unit_x_range`). 카메라·지그가 고정이라 검사 대상 보드가 항상 중앙 부근에 온다는 가정이며, 부품 개수·조명에 흔들리지 않는다. 실제 검사 라인은 지그에 보드가 하나만 고정되므로 애초에 후보가 하나뿐이라 이 문제 자체가 없다.
>
> `board_detect.py`의 홀 검출은 실제 사진 4장(부품 없는 보드, 부품 많은 보드 3장)에서 검증됐다 — IC·LED·커패시터로 홀이 가려져도 정렬이 유지된다. (원근 변환으로 이미지를 평탄화하는 방법도 시도했는데, 부품 많은 사진에서 렌즈 왜곡을 오히려 증폭시키는 걸 확인하고 뺐다 — WORKLOG.md 참고.)
>
> 90도 회전 후 미세 기울기 보정(`rail_detect.measure_tilt_angle`)까지 넣고 나니, 핀홀 위치 평면 피팅의 x축 기울기 계수(`b2`)가 사진 전체 폭 기준으로 최대 10px 이내로 줄었다 (도입 전엔 최대 ~24px). 완전히 0이 되진 않는데, 각도 측정 자체의 측정 오차(레일 선 폭 15px 구간만 보고 재는 정밀도 한계)로 보이며 홀 하나 크기(~50px)보다 훨씬 작아 실사용에 문제없다.
