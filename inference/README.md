# 추론 서비스 (Python)

- 담당:
- 기술: Python, FastAPI, YOLO
- 포트: 8001

스테이션(C#)이 정렬된 보드 이미지를 보내면, **어느 핀홀에 어떤 부품이 꽂혀 있는지**를
반환한다. 장착 상태가 맞는지 틀린지 "판정"(PASS/FAIL)은 하지 않는다 — 그건 스테이션의 몫이다.
모델 가중치와 데이터셋은 Git에 올리지 않는다.

API 계약(요청/응답 형식)은 [docs/api-contract.md](../docs/api-contract.md) 참고.

## 왜 이런 방식인가 — 지그·카메라 고정 전제

이 시스템은 사용자가 자유롭게 촬영하는 일반 사진 인식 서비스가 아니라, **검사 지그와
카메라가 고정된 생산 환경**을 전제로 한다. 검사할 브레드보드 단위와 영상 안의 대략적인
위치·크기가 이미 정해져 있으므로, 매번 전체 이미지에서 보드를 새로 찾는 범용 검출
모델을 쓸 필요 없이, **정해진 검사 범위를 기준으로 필요한 부분만 빠르고 일관되게
잘라내는 것**이 목표다.

다만 카메라·지그가 고정이어도 장착 오차·진동·촬영 시점·카메라 기종 차이 때문에 영상이
몇십 픽셀 밀리거나 살짝 기울거나(때로는 90도 단위로 방향 자체가) 달라질 수 있다.
전처리는 검사 영역을 매번 새로 판단하는 게 아니라, 이런 **작은 차이만 실측해서 보정**하는
데 목적이 있다:

- 검사 대상은 항상 프레임 중앙 부근에 있다는 지그 가정으로 가운데 단위를 선택한다.
- 빨강·파랑 전원 레일의 실제 위치를 찾아 좌우 이동을 보정한다.
- 레일 선의 기울기를 재서 회전 오차를 보정한다 (카메라가 어느 방향으로 눕혀 찍든
  0/90/180/270도 중 레일·라벨이 다 맞는 방향을 먼저 찾은 뒤, 그 안에서 미세 각도를 잰다).
- **행 번호 라벨("10"~"30")의 실제 위치를 OCR로 읽어서, 세로 크롭 범위뿐 아니라
  핀홀 행 위치 계산 자체의 기준점(앵커)으로도 쓴다** — 아래 "숫자를 앵커로 쓰는 이유" 참고.
- 어느 단계든 실패하면 고정 카메라 환경에서 실측해둔 예비값으로 동작을 계속한다.

카메라 위치·지그 구조가 크게 바뀌거나 임의의 각도·거리에서 촬영한 이미지까지 지원해야
한다면, 지금의 임계값들을 다시 실측하거나 별도의 보드 검출 방식이 필요하다.

### 숫자(라벨)를 앵커로 쓰는 이유

핀홀 282개의 **행(가로줄) 위치**는 원래 "각 열(세로줄)에서 검출된 홀들 중 마지막 점이
곧 마지막 행(U)이다"라고 역산해서 추정했다. 그런데 실측해보니 이 가정이 깨지는 경우가
여럿 있었다:

- 부품(IC 다리 등)이 열의 끝부분을 가려서 실제보다 일찍 끊기는 경우
- 레일 열이 단자부 열과 물리적으로 다른 길이로 끝나는 보드
- 노이즈(실크스크린 반사 등)가 원래 비어있어야 할 자리에 뭉쳐서 열처럼 잡히는 경우

이런 경우 열 하나의 데이터만으로 그 열 자신의 기준점을 추정하면, 그 오차가 행 전체
계산에 그대로 번진다(핀홀들이 한 칸씩 밀리거나 한 행이 휘어 보임).

그래서 지금은 **실크스크린에 인쇄된 "10"·"15"·"20"·"25"·"30" 라벨 자체의 실제 위치를
OCR로 읽어서, 그걸 행 위치 계산의 1차 기준점(앵커)으로 직접 쓴다.** 이 라벨은 어떤
열의 검출 결과에도 의존하지 않는 독립된 관측값이라, 위 세 가지 경우 어디에도 흔들리지
않는다. 라벨 앵커가 부족하거나(3개 미만) 신뢰할 수 없어 보이면(같은 x 근처에만
몰려있어 기울기를 못 잡거나, 그 결과로 재배정한 핀홀 수가 너무 적으면) 자동으로 예전
방식(열 기반 추정)으로 되돌아간다.

## 단계별 설명

### 0. 전처리 — 방향 판별 + 크롭 (`roi.py`, `rail_detect.py`, `label_detect.py`)

| 보정 | 방법 | 왜 필요한가 |
|---|---|---|
| **방향 판별** | 0/90/180/270도를 다 시도해서, 레일(색상)도 찾아지고 라벨(OCR)도 읽히는 방향을 채택 (`roi._find_orientation`) | 카메라 기종이 바뀌면 사진이 눕는 방향 자체가 달라질 수 있다(실측: 4032×3024 사진은 반시계 90도가 정답, 새 720×720 사진은 회전 없음이 정답). OCR 성공 여부가 방향 검증 수단도 됨 — 방향이 틀리면 숫자가 거꾸로/옆으로 찍혀 거의 못 읽는다 |
| **미세 기울기(deskew)** | 선택된 단위의 좌우 경계 레일 선 기울기를 재서(`rail_detect.measure_tilt_angle`) 한 번 더 돌림 | 큰 방향만 맞춘 것으로는 카메라 장착 각도 오차(-1~+1도 정도)가 남는다 |
| **가로 크롭** | 빨강/파랑 전원 레일 선을 HSV 색상으로 찾아, 후보 단위 중 **프레임 중앙에 가장 가까운 것**을 선택 | 카메라가 조금만 밀려도(±40px) 고정 픽셀 값으로는 못 버틴다 |
| **세로 크롭 + 라벨 앵커** | 행 번호 라벨(10,15,20,25,30)을 OCR로 읽어서 그 간격으로 계산. 이때 찾은 라벨의 (x,y) 원본 위치도 같이 보존해서 1단계로 넘긴다 | 카메라 위치·줌이 사진마다 달라 고정 범위로는 마지막 행이 잘리기도 한다. 라벨 5개 중 2개 이상 찾으면 선형회귀, 1개만 찾아도 기본 피치로 나머지 추정 — 폰트가 달라 하나를 못 읽어도 나머지로 버틴다 |

모든 단계가 실패하면 각각의 예비 고정값(`FALLBACK_X_RANGE`, `Y_RANGE`)으로 대체된다.
사진 해상도가 낮아도 카메라가 더 가까이서 찍으면(줌인) 실제 홀 피치는 기준 사진과
비슷하거나 더 클 수 있어서, 이후 단계의 픽셀 기반 상수들은 해상도 비율이 아니라
**OCR로 실측한 행 피치**를 기준값과 비교한 배율(`scale.py`)로 조정한다.

### 1. 핀홀 위치 계산 (`board_detect.py`)

크롭된 이미지 **자체는 변형하지 않고**, 그 안에서 홀(구멍) 282개의 픽셀 위치를 직접 계산한다.

- **열(세로줄) 위치**: 홀 blob들의 x좌표를 간격 기반으로 그룹핑한다(균등 분할 아님 — 단자부
  채널 때문에 열 1~2, 6~7, 11~12 사이가 특히 넓음). 부품에 가려 조각난 열은 피치 기반으로
  다시 합치고, 그래도 개수가 안 맞으면(많거나 적으면) x폭 이상치 제거·산수 보간·실측 조각
  우선 채택 순으로 보정한다. 개수는 맞아도 조각이 억지로 병합돼 위치 자체가 흔들린 열은
  IQR(사분위 범위)로 "애매한 열"로 표시해두고, **같은 물리적 구간(레일 2열/단자부 5열)
  안의 확실한 열**을 기준으로 정상 피치에 맞춰 재배치한다 — 구간 경계(위에서 말한 넓은
  채널)를 넘어서까지 균등하게 나누면 그 넓은 간격 자체를 뭉개버리므로, 재배치는 항상
  구간 안에서만 한다.
- **행(가로줄) 위치**: 모든 열의 모든 홀을 한꺼번에 모아서 `y = b0 + b1·행번호 + b2·x`
  평면 하나를 최소제곱으로 피팅한다. 평면 하나로 모든 위치를 계산하므로 **같은 행(알파벳)은
  항상 일직선**이 된다. 1차 피팅 기준점은 위에서 설명한 **라벨 앵커 우선, 안 되면 신뢰
  가능한 열 기반 역산으로 폴백**. 1차로 대략 맞춘 평면으로 전체 홀의 행 번호를 다시
  매긴 뒤 재피팅해서, 1차에서 못 믿었던 열의 위치도 결국 바로잡는다.
- 레일 열(0,1,12,13)은 E/K/Q 행이 없어서 18칸뿐인데, 물리적 간격은 20칸(건너뛴 자리도
  칸 너비를 차지)이라는 점을 반영해서 계산한다.

네 모서리 호모그래피나 원근 변환으로 이미지를 평면화하는 방법도 시도했지만,
실측 사진에서 더 부정확하거나 오히려 왜곡을 키우는 걸 확인하고 지금 방식으로
정착했다 (그때 쓰던 `calibration.py`는 삭제됨). 자세한 시행착오는
[WORKLOG.md](WORKLOG.md) 참고.

### 2. 부품 탐지 (`main.py`의 `detect_parts`)

평탄화(변형)되지 않은 크롭 이미지를 YOLO(`yolo8n.pt`, `black_wire`/`capacitor`/`ic_chip`/
`led`/`red_wire`/`resistance330`/`resistance470`/`white_wire` 8종 학습)에 넣어, 부품
종류·신뢰도·픽셀 박스를 얻는다. 모델은 서버 시작 후 최초 1회만 로딩해서 재사용한다.
모델 파일 경로는 `YOLO_MODEL_PATH` 환경변수로 바꿀 수 있고, 기본값은
`inference/app/models/yolo8n.pt` (Git에는 안 올라감, 로컬에 직접 둬야 함).

### 3. 홀-박스 대조 (`board.py`)

"박스 중심과 가장 가까운 핀홀 하나"를 고르는 대신, 반대로 **핀홀마다 어떤 박스 안에
들어가는지**를 본다. 박스 안에는 부품 몸통 크기 때문에 실제 다리 개수보다 핀홀이 더
많이 잡힐 수 있어서, 부품 종류별로 "그중 실제 다리가 꽂힌 핀홀"만 거르는 규칙을 둔다:

| 부품 종류 | 다리 개수 | 거르는 방법 |
|---|---|---|
| `led`, `capacitor` | 2 | 몸통이 둥글어 여러 핀홀에 걸치지만 다리는 몸통 중심 바로 아래로 나온다 → **박스 중심에서 가장 가까운 2개** |
| `black_wire`, `red_wire`, `white_wire`, `resistance330`, `resistance470` | 2 | 길쭉한 몸통 양 끝에만 다리가 있다 → 박스의 긴 축(가로/세로 중 더 긴 쪽) 방향으로 정렬해서 **양 끝 2개** |
| `ic_chip` | 14 | 다리가 몸통 양옆(가장 바깥쪽 두 열)에만 있다 — 중간 열은 몸통에 가려진 빈 핀홀이다 → 후보를 바깥쪽 두 열로 먼저 좁힌 뒤 **박스 중심에서 가장 가까운 14개** |

가려진(=다리가 꽂힌) 핀홀만 골라 `{pinhole, class, confidence}` 배열로 응답한다. 부품
하나가 다리를 여러 개 쓰면 그 개수만큼 배열 원소가 나뉘어 나온다 (API 계약은
[docs/api-contract.md](../docs/api-contract.md) 참고).

**같은 부품의 중복 탐지 제거 (`main.py`의 `_deduplicate_boxes`)**: YOLO가 부품 하나를
박스 여러 개로 중복 탐지하면(실측: IC칩 하나가 신뢰도 0.96/0.28 박스 2개로, 저항 하나가
`resistance470`(0.70)/`resistance330`(0.47) 박스 2개로 잡힌 사례), 위 다리 거르기가
박스 단위로 동작하기 때문에 박스마다 따로 다리를 채워서 실제보다 더 많은 핀홀이 장착된
것처럼 나올 수 있다. 그래서 다리를 거르기 전에, **겹침 비율(IoU)이 0.5 이상인 박스는
클래스가 달라도** 신뢰도가 가장 높은 것만 남기고 나머지는 버린다 — 실제 부품은 한
자리에 하나만 있을 수 있으므로, 위치가 거의 같으면 YOLO가 클래스를 다르게 헷갈렸어도
같은 물체의 중복 탐지로 본다.

달라도 핀홀 위치가 픽셀 단위로 정확히 맞고, IC·LED·커패시터로 홀이 가려져도 정렬이
유지된다.

## 환경 준비

`pytesseract`는 pip 패키지일 뿐이고, 실제 OCR 엔진인 **Tesseract 실행 파일이 별도로 설치**돼 있어야 한다.

```
conda install -c conda-forge tesseract
```

(Windows 설치 프로그램을 써도 된다.) `label_detect.py`가 conda 환경 경로 기준으로 실행파일·언어 데이터 경로를 자동으로 잡아준다.

YOLO 추론에는 `ultralytics`가 필요하다 (`pip install ultralytics`). 모델 가중치
(`.pt`)는 Git에 올라가지 않으므로, `inference/app/models/`에 직접 받아서 넣어야 한다.

## 알려진 한계

- 부품에 심하게 가려 실제 검출된 홀이 3개 미만인 열은, 산수로 추정한 위치를 쓴다 —
  드물지만 그 자리에 실제 조각이 남아있으면 실측값을 우선하고, 없으면 피치 기반 추정치를 쓴다.
  이 위치가 애매한 열로 표시되면 같은 구간 안의 확실한 열을 기준으로 다시 보정하지만,
  양쪽(또는 한쪽)에 같은 구간의 확실한 열이 아예 없으면(예: 구간 전체가 가려짐) 보정 없이
  그대로 쓴다.
- 크롭 여백을 너무 넉넉히 주면(레일 열의 마지막 홀 하나를 더 담으려고 시도했던 것)
  사진에 따라 위아래 인접 보드 유닛의 내용까지 크롭에 딸려 들어올 수 있어, 지금은
  다소 보수적인 여백을 쓴다 — 아주 드물게 레일 열의 마지막 홀 하나를 놓칠 수 있다.
- `_deduplicate_boxes`는 **겹침(IoU 0.5 이상)이 있는 박스만** 같은 물체의 중복으로 본다.
  YOLO가 같은 물체를 놓고 클래스만 헷갈린 게 아니라, 완전히 다른 자리에서 아예 다른
  종류로 잘못 인식하는 경우(실측: 전선 하나가 별도 위치에서 `ic_chip`으로도 잘못
  탐지된 사례)는 겹침이 없어서 이 로직으로 걸러지지 않는다. 여러 YOLO 모델(yolo8n/
  yolov9m/yolo12m/yolo26m)을 실측 비교했을 때도 이런 클래스 오분류가 종종 관찰됐다 —
  근본적으로는 학습 데이터·모델 품질 문제라 후처리만으로 완전히 해결하기는 어렵다.
