  - 열 구조: 0·1 = 왼쪽 전원 레일, 2~6 = 왼쪽 단자부, 7~11 = 오른쪽 단자부, 12·13 = 오른쪽 전원 레일

  - (처음엔 행/열을 반대로 짰다가 — 즉 글자를 열, 숫자를 행으로 — 사용자가 좌표표 이미지를 보내줘서 바로잡음)
  - **미해결**: YOLO 박스의 "픽셀 좌표" → 이 "그리드 좌표(row_index, col_index)"로 바꾸는 보정(calibration) 단계가 아직 없음. 스테이션이 기준 마크로 정렬해서 보내지만 촬영마다 핀홀 픽셀 위치가 미묘하게 달라서, 고정 픽셀 원점/간격을 하드코딩할 수 없음. 이미지별로 기준 마크(또는 핀홀 자체)를 다시 검출해서 homography/스케일을 계산하는 단계 필요. (물리적 핀홀 간격은 실제 브레드보드와 동일한 2.54mm 피치)

### 머신비전 구성 개념 정리

무엇이 딥러닝이고 무엇이 규칙 기반(전통적 이미지 처리)인지 헷갈리지 않도록 정리:

- **딥러닝**: YOLO 객체 탐지 — 이미지에서 부품 종류·위치(박스)·신뢰도를 검출. (`detect_parts`, 아직 미구현)
- **전통적 머신비전(규칙 기반)**: 기준 마크/핀홀 자체를 찾는 것, 원근 보정(homography)으로 픽셀 → 그리드 좌표 변환. (`find_board_corners`, `calibration.py`)

- **FastAPI**: 머신비전 모델이 아니라, C# 스테이션과 Python 추론 코드를 연결하는 API 서버일 뿐
- **PASS/FAIL 판정**: 딥러닝도 이 서비스도 아니고, C# 스테이션의 규칙 엔진이 담당

즉 "브레드보드 구조화" 전체가 머신비전 작업이긴 하지만, 그 안에서도 딥러닝(부품 인식)과 기하학/OpenCV(좌표 변환)와 순수 후처리(구조화)가 나뉘어 있다. 나중에 모델이 핀홀·단자 키포인트까지 직접 검출하도록 학습시키면 그 부분도 딥러닝이 되겠지만, 검출 좌표를 핀홀 이름으로 바꾸는 마지막 단계는 그래도 규칙 기반으로 남을 수 있다.

### 자동 보드 크롭·홀 좌표 표시를 위한 대안 검토

- 코드 변경 없이 개념만 검토함.
- 딥러닝을 쓰는 권장 방식: `YOLO-Pose` 같은 키포인트 모델이 보드와 네 모서리 핀홀(A0, A13, U0, U13)을 검출한다.
- 검출한 네 점으로 homography를 계산해 보드를 표준 크기로 원근 보정·크롭하고, 알려진 A~U/0~13 격자를 이미지 위에 투영한다.
- 이 방식에서 보드/모서리 검출은 딥러닝이고, 크롭·원근 보정·홀 좌표 표시는 기하학적 후처리다.
- 대안으로 `YOLO-Seg`/Mask R-CNN을 이용해 보드 외곽 마스크를 찾을 수 있으며, 모든 핀홀을 직접 검출하는 모델은 가림과 라벨링 비용 때문에 우선순위가 낮다.
- 카메라와 지그가 고정되고 보드에 표식을 붙일 수 있다면 ArUco/AprilTag가 딥러닝보다 간단하고 안정적인 선택이다.
- 실제 요구사항은 큰 보드 전체가 아니라 가운데의 검사 대상 구역만 크롭하는 것임. 따라서 전체 보드 네 모서리 검출보다 2단계 coarse-to-fine 방식이 적합하다.
- 1단계: 축소한 전체 이미지에서 YOLO-OBB/YOLO-Seg 등으로 검사 대상 구역을 찾는다. 2단계: 검출 좌표로 원본 고해상도 이미지를 크롭하고, 크롭 내부의 로컬 기준점 또는 레일/핀홀 격자로 homography를 계산한다.
- 크롭 안에 전체 보드 모서리가 없다면 A0/A13/U0/U13을 전체 보드 모서리로 찾는 방식은 사용할 수 없다. 검사 구역 주변에 로컬 기준 마크를 두거나, 레일과 반복 핀홀 격자를 검출해 좌표 기준을 복원해야 한다.
- 제공된 실제 사진은 동일한 브레드보드 단위가 가로로 연속된 구조다. 각 단위의 빨강/파랑 전원 레일이 비교적 뚜렷하므로, 모든 단위 후보를 검출한 뒤 중심점이 이미지 중심에 가장 가까운 단위를 선택해 크롭하는 방식이 가능하다.
- 고정 환경에서는 레일 색상 검출 + 중심 단위 선택이 가장 단순하다. 조명·기울기 변화가 크면 YOLO-OBB/YOLO-Seg로 각 단위의 사각형/마스크를 검출하고 중심 단위를 고른 뒤, YOLO-Pose 또는 로컬 기준점으로 원근 보정한다.
- 반복 무늬만으로는 어느 단위가 검사 대상인지 의미적으로 구분할 수 없으므로, `화면 중심에 가장 가까운 단위`, `왼쪽에서 N번째 단위` 같은 선택 규칙이나 별도 마커가 필요하다.

### 스테이션과 핀홀 값으로 통신하는 이유

- 픽셀 좌표는 카메라 해상도, 크롭 위치, 거리, 기울기와 원근에 따라 매 촬영마다 바뀌지만 `J9` 같은 핀홀 라벨은 물리적 위치를 나타내므로 안정적이다.
- 추론 서비스가 영상 좌표 보정 책임을 맡고, C# 스테이션은 카메라 세부사항 없이 레시피의 기대 핀홀과 실제 핀홀을 직접 비교할 수 있다.
- 핀홀 라벨은 사람이 읽고 로그·DB·오류 화면에서 추적하기 쉽고, API 데이터도 단순해진다.
- 픽셀은 추론 서비스 내부 계산과 디버깅에 계속 사용되며, 최종 API 경계에서 도메인 좌표인 핀홀 값으로 변환한다.
- 단점은 보정이 틀리면 잘못된 핀홀로 양자화될 수 있다는 점이므로 신뢰도와 필요시 디버그용 픽셀 박스를 별도로 보존하는 것이 좋다.

### 원근 펼치기 도입 + calibration.py 설계 결함 발견

- 크롭된 이미지가 살짝 기울어져 있어서(카메라 각도), 축 정렬된 사각형 크롭이 왼쪽·오른쪽에서 다른 높이를 잘라 오른쪽 상단 핀홀이 살짝 잘리는 게 눈에 띔
- 네 모서리 핀홀(A0/A13/U0/U13)을 홀 blob 검출로 찾은 뒤 `cv2.getPerspectiveTransform` + `warpPerspective`로 평면처럼 펴봄(원근 펼치기) → 확실히 더 정확해짐 (좌우 레일이 같은 높이로 맞춰짐)
- 이 과정에서 `calibration.py`의 근본적인 한계를 실측으로 발견함: **이 브레드보드는 열 6과 7 사이에 단자부 채널(물리적으로 넓은 갭)이 있어서 열 간격이 균등하지 않은데, `calibration.py`는 네 모서리(열 0·13)만으로 호모그래피를 계산해서 열 인덱스(0~13)가 균등한 간격이라고 가정한다.** 같은 네 모서리로 `calibration.py`를 그대로 돌려보니, 갭을 지나면서 오차가 누적돼서 원근 펼치기 전보다도 부정확했음
- 결론: **기울기(회전)는 호모그래피로 보정할 수 있지만, 열 간격의 비균등성은 호모그래피 하나로 표현 못 하는 별개의 문제.** 열 간격은 실제로 검출한 값을 써야 함
- [app/board_detect.py](app/board_detect.py) 신규 작성 — 정확도가 확인된 방식을 정식 모듈로 formalize:
  1. `_find_hole_centroids`: 홀 blob 전부 검출 (기존 dev 스크립트 로직을 정리)
  2. `_pick_extreme_corners`: 볼록 사각형 꼭짓점 성질(x+y, -x+y, x-y, -x-y 최소화)로 네 모서리 자동 선택
  3. `_flatten`: 네 모서리로 원근 변환해서 기울기만 보정 (열 간격 보간에는 안 씀)
  4. `_fit_grid`: 평탄화된 이미지에서 다시 홀 검출 → 열은 실제 k-means 클러스터 x좌표 그대로 사용(비균등 간격 보존), 행은 물리적으로 균등하므로 첫/끝 행 중심 사이를 선형보간
  5. `find_pinhole_pixels(image)`: 위 전부를 묶어서 `{라벨: (x,y)}` 282개 + 평탄화된 이미지 반환

- 게다가 행 y좌표를 모든 열을 합쳐서 한 번에 전역 k-means로 구했던 것도 이 왜곡을 더 섞이게 만든 원인이었음
- **결론 및 조치**: 원근 변환(perspective warp)을 완전히 제거함. [app/board_detect.py](app/board_detect.py)를 다시 작성해서, 이미지를 펴지 않고 **열마다 독립적으로** 그 열 자신의 첫 홀~마지막 홀 사이를 선형보간하도록 변경 (열 사이 기울기 차이가 있어도 이미지 변형 없이 그대로 반영됨). `find_pinhole_pixels`가 반환하는 `image`는 이제 입력과 동일함(변형 없음) — `board.py`, `main.py`도 이에 맞춰 갱신 (더 이상 "평탄화된 이미지"라는 개념이 없음)
- 이 과정에서 **열 검출(`_fit_columns`) 자체의 버그도 하나 더 발견**: 처음엔 x좌표에 k=14 고정 k-means를 썼는데, 보드 실크스크린에 인쇄된 행 번호 숫자("10","15","20",...)가 어두운 blob으로 오검출돼서 노이즈로 섞여 들어가면, 근처 실제 열의 k-means 중심이 최대 13px까지 밀리는 걸 확인함 (`basic_board`의 열 11이 867.4로 밀렸던 것 — 실제로는 853.5가 맞음). 숫자 라벨은 실제 열보다 검출 개수가 훨씬 적다는 점(전체 21행 중 1~2곳에서만 나타남)을 이용해서, k-means 대신 **x좌표 정렬 후 간격 기반 그룹핑**(`rail_detect.py`의 레일선 클러스터링과 같은 원리) + 그룹 크기가 너무 작으면(<10) 잡음으로 버리는 방식으로 교체함. 두 사진 모두 정확히 14열이 검출되는 것으로 검증함
- 결과물 이름도 정리: `*_flattened.jpg`는 더 이상 안 만들고, `basic_board_pinholes.jpg`/`board1_pinholes.jpg`로 통일
- 교훈: 어떤 보정 기법(원근 변환 등)이 "이론적으로 맞아 보인다"고 해서 실제로 더 정확해지는 건 아니다 — 반드시 다른 사진(특히 더 복잡한/노이즈 많은 사진)으로도 실측 비교해야 함. `basic_board.jpg`(단순한 사진) 하나만으로 좋아 보였던 방법이 `board1.jpg`(복잡한 사진)에서 깨진 사례

### 진짜 원인 발견: 레일 열 보간 계산 자체가 틀렸었다 (렌즈 왜곡 아님)

- 위 수정 후에도 사용자가 `board1.jpg`에서 여전히 핀홀이 안 맞는다고 확인 (오른쪽 레일 열 쪽, "10" 라벨 위 핀홀들이 눈에 띄게 어긋남). 처음엔 "렌즈 왜곡 때문에 열 안에서도 피치가 변한다"고 오판했었는데, 실측해보니 **훨씬 단순하고 결정론적인 버그**였음
- 원인: 레일 열(0,1,12,13)은 E/K/Q 행이 빠져서 `expected_rows`가 18개뿐인데, 코드가 `np.linspace(첫홀, 마지막홀, len(expected_rows))`로 **"17칸 균등 간격"**으로 나눴음. 그런데 실제로는 D→F, J→L, P→R 사이가 (건너뛴 E/K/Q 자리만큼) 물리적으로 2칸 너비라서, 진짜 물리적 간격은 20칸임. 이 불일치 때문에 매 칸마다 조금씩 어긋난 게 누적되어, 레일 열 아래로 갈수록 점점 크게 밀렸던 것. (단자부 열 2~11은 21행이 다 있어서 이 버그의 영향이 전혀 없었고, 그래서 가운데는 항상 잘 맞아 보였던 것도 이걸로 설명됨)
- 수정 ([app/board_detect.py](app/board_detect.py) `find_pinhole_pixels`): `expected_rows` 안에서의 순번이 아니라, `pinhole_grid.ROWS`(A~U, 21개) 안에서의 **진짜 물리적 인덱스**를 기준으로 보간하도록 변경. 구체적으로 `np.linspace(첫홀, 마지막홀, 21)`로 21칸 전체를 만든 다음, 각 행 글자의 실제 인덱스(E=4,K=10,Q=16 스킵)로 값을 골라 쓰는 방식
- 검증: `board1.jpg`의 A13 쪽 레일 열에서 재확인 — 수정 전엔 맨 위 모서리(A13)에 실제 홀이 안 보이고 그 아래 점들도 계속 한 칸씩 밀려 보였는데, 수정 후엔 모든 행에서 정확히 홀 중앙에 점이 찍힘. `basic_board.jpg`도 재확인 완료, 두 사진 다 레일 열까지 포함해서 정확히 맞음
- 교훈: "이 사진에선 잘 맞아 보인다"가 아니라, **실제 계산 로직을 손으로 다시 검산**해야 하는 종류의 버그였음. 특히 이번처럼 "칸 개수로 나누기" 같은 계산은 물리적 구조(스킵된 행 등)를 다시 한번 명시적으로 확인해야 함
- 사용자가 함께 물어본 것: "YOLO-OBB/YOLO-Seg를 쓰는 게 나을까?" → 답변: OBB/Seg는 "이 보드가 어디 있는지"(바운딩박스/마스크) 찾는 모델이라 지금 겪는 문제(핀홀 282개의 서브픽셀 정확한 위치)와는 결이 다름. 이 문제에 맞는 딥러닝 도구는 키포인트 검출(YOLO-Pose류)이지만, 핀홀 위치를 라벨링한 학습 데이터가 아직 없어서 투자 비용이 큼. 이번 버그는 순수 계산 오류였고 고치고 나니 실측 사진 2장 모두 완벽히 맞아서, 지금 시점에 딥러닝 전환의 필요성은 낮다고 판단 — README.md에도 같은 결론 정리함

### 두 번째 실제 버그: 열마다 "여분의 홀"이 낄 수 있다는 걸 놓침

- 사용자가 위 수정 후에도 재확인: "오른쪽으로 가면 왜곡 생기잖아. 오른쪽 숫자 10 라인의 가장 오른쪽 핀이 A13인데 그 윗줄 핀홀까지 보여." → `board1.jpg`를 다시 실측
- 원인: 카메라가 살짝 기울어져 있어서, 고정 `Y_RANGE`로 자른 크롭의 위쪽 경계가 열마다 다른 실제 행에서 잘림. 오른쪽 4개 열(10,11,12,13, 즉 두 번째 단자부 오른쪽 절반 + 오른쪽 레일)은 크롭에 **행 A보다 한 칸 위의 진짜 홀이 하나 더 딸려 들어와 있었고**, 코드가 "이 열에서 검출된 제일 위 홀 = 행 A"라고 가정했기 때문에 이 여분의 홀을 A로 잘못 인식해서 그 아래 전체가 한 칸씩 밀렸음. (왼쪽 10개 열은 이 여분의 홀이 없어서 멀쩡했음 — 그래서 왼쪽은 계속 잘 맞아 보였던 것)
- 수정 ([app/board_detect.py](app/board_detect.py) `find_pinhole_pixels`): 전역 칸 간격(피치)을 모든 열의 실측 간격(중복 제거 후, 35~70px 범위만 필터링)에서 median으로 추정한 다음, 열마다 **반대쪽 끝(신뢰할 수 있는 쪽) + 전역 피치로 "진짜 행 A/U가 있어야 할 위치"를 역산**해서 그 범위를 벗어난 여분의 홀은 걸러내고 나서 보간하도록 변경. 중첩 컨투어(같은 홀이 두 번 검출되는 것)를 먼저 합치는 `_dedup`도 추가함
- 검증: `board1.jpg`의 A13이 이제 왼쪽 A0와 정확히 같은 높이(진짜 행 A)에 찍힘, 그 아래 전체 열도 실제 홀과 정확히 일치. `basic_board.jpg`는 원래 이 문제가 없었고 회귀도 없음을 재확인
- 교훈: "카메라·지그가 고정이라 세로 크롭도 고정값으로 충분하다"는 가정이 실제로는 미묘한 기울기 하나로 깨질 수 있다는 걸 두 번째로 확인함(첫 번째는 가로 크롭 때). 다만 이번엔 크롭 자체를 고치는 대신(카메라마다 다시 튜닝해야 해서 비용이 큼), **알고리즘이 "크롭에 의도한 범위 밖 홀이 한두 개 더 있을 수 있다"는 걸 전제하고 스스로 걸러내도록** 만들어서 더 근본적으로 해결함

### 세 번째 실제 버그이자 진짜 근본 원인: "열마다 따로 계산"이 원천적으로 잘못된 설계였다

- 사용자가 위 수정 후에도 재확인하면서 결정적인 제약을 하나 알려줌: **"같은 알파벳(A~U)의 핀홀은 같은 직선상에 있어야 한다."** 실측 사진에 분홍색으로 진짜 U13 위치를 표시해서 보내줌 — 우리가 찍은 점과 어긋나 있었음
- 이 제약을 듣고 나서야 설계 결함을 깨달음: 그동안 "열마다 따로" 그 열 자신의 첫 홀~마지막 홀 사이를 선형보간해왔는데, 이러면 **열 A의 보간 결과와 열 B의 보간 결과가 서로 다른 열에서 계산되기 때문에, 같은 행(예: K행)이라도 열마다 y값이 조금씩 달라질 수 있음** — 이게 "같은 행은 일직선이어야 한다"는 물리적 제약을 구조적으로 보장하지 못하는 원인이었음. `board1.jpg`에서 열 20번(K행 부근) 근처가 왼쪽은 멀쩡한데 오른쪽 몇 개 열에서만 15~20px 위로 어긋나 있던 것도 이 때문 — 렌즈 왜곡이 아니라, 열마다 독립적으로 계산한 결과가 우연히 그 지점에서 어긋난 것
- 수정 ([app/board_detect.py](app/board_detect.py) `_fit_row_plane`): 열마다 따로 계산하는 대신, **모든 열의 모든 홀을 한꺼번에 모아서 `y = b0 + b1*행번호 + b2*x` 평면 하나를 최소제곱으로 피팅**하도록 완전히 바꿈. 각 홀이 몇 번째 행인지는 그 열의 반대쪽 끝(신뢰할 수 있는 쪽) + 전역 피치로 역산해서 추정(이전 버그 수정 로직 재사용). 평면 하나로 모든 위치를 계산하므로, **같은 행번호는 정의상(수학적으로) 항상 일직선** — 열마다 다른 결과가 나올 수 없는 구조로 바뀜. 이상치(occlusion 등으로 잘못 매칭된 점)는 1차 피팅 후 잔차 15px 넘는 것만 제외하고 재피팅
- 검증: `board1.jpg`에서 이전에 어긋났던 지점(K행 부근 오른쪽 열들)까지 포함해서 전부 홀 중앙에 정확히 맞음. `basic_board.jpg`도 회귀 없음. 평면 피팅 잔차: 이상치 제거 전 표준편차 ~5.8px(최대 ~29px), 실사용에 충분히 정확
- 교훈: 데이터를 더 많이 실측하는 것보다, **사용자가 알려준 "물리적으로 당연한 제약"(같은 행은 일직선)을 알고리즘 설계에 명시적으로 반영하는 게 훨씬 근본적인 해결책**이었다. 열별 독립 계산은 "열마다 다를 수 있다"는 유연성이 오히려 이 제약을 깨는 자유도가 되어버렸음

- 실측으로 확인해봄: `roi.Y_RANGE`에 위아래 마진을 40~120px 더 줘서 board_detect가 알아서 A~U만 골라내는지 테스트

- 원인: 지금 "여분의 홀 거르기"(`_fit_row_plane`의 `predicted_top` 로직)는 "카메라가 살짝 기울어져서 한 칸 정도 여분이 있을 수 있다"는 **작은 오차만** 보정하도록 설계됨 — 반대쪽 끝(예: 열의 마지막 점)을 무조건 "진짜 U"라고 믿고 역산하는 방식이라, 마진을 크게 주면 그 "무조건 믿는 반대쪽 끝"조차 여분의 홀일 수 있어서 기준 자체가 틀어짐
- 결론: 사용자 아이디어(라벨로 세로 범위를 실제로 찾기)는 방향은 맞지만, 지금 알고리즘은 그걸 흉내만 낼 뿐(작은 오차 보정) 넓은 범위에서 "10~30이 진짜 어디 있는지" 찾아내진 못함. 진짜로 하려면 OCR이나 숫자 템플릿 매칭으로 "10"/"30" 라벨의 실제 위치를 읽어야 함 (가로 크롭의 레일 색 검출과 동급의 신뢰도를 세로에도 주려면 이 작업이 필요)
- **결정**: 지금은 투자하지 않기로 함 — "카메라·지그가 고정이라 세로 위치는 안 바뀐다"는 원래 설계 전제를 그대로 유지하기로 사용자가 확인함 (`margin=0`, 즉 지금 `roi.Y_RANGE` 값에서는 두 사진 다 정확히 맞는 것도 재확인됨). 나중에 카메라를 다시 장착하거나 여러 라인에 배포하게 되면, 그때 OCR 기반 세로 검출을 추가하는 걸로 미뤄둠

- 실측: `board2.jpg`는 조명이 고르지 않아서, 실제로는 레일 선이 여러 쌍 있는데도 `_MIN_LINE_HEIGHT_RATIO=0.5`(세로로 50% 이상 이어져야 선으로 인정) 기준을 다 못 넘김 — 채도가 군데군데 끊겨서 30%대에 걸리는 선이 많았음

### OCR(Tesseract)로 "10"·"30" 라벨을 읽어서 세로 크롭 범위 계산

- 환경 준비: `pytesseract`(pip) + Tesseract 엔진 실행파일이 별도로 필요함. `conda install -n pcb-aoi -c conda-forge tesseract`로 설치 (버전 5.5.3). Windows에서 conda-forge 패키지의 tessdata 경로가 실행파일 기준 기본 탐색 경로와 달라서 `TESSDATA_PREFIX` 환경변수를 명시적으로 잡아줘야 했음 — [app/label_detect.py](app/label_detect.py)가 `sys.executable`(현재 conda 환경의 python.exe) 기준으로 실행파일·tessdata 경로를 자동으로 찾아서 설정하도록 만듦(수동 환경변수 설정 불필요)
- 실측: 넓은 세로 범위(`roi.Y_RANGE` ±400px)에서 가로로 이미 찾은 유닛(x1~x2) 폭만큼만 OCR을 돌려보니, "10"·"15"·"20"·"25"·"30" 텍스트를 신뢰도(conf) 88~96으로 안정적으로 읽음. 왼쪽 라벨은 근처 홀과 겹쳐서 잡음이 섞였지만(`"158"`, `"308"` 등으로 오검출), 오른쪽 라벨은 깨끗하게 읽힘 — 그래서 신뢰도 임계값(80)으로 걸러내면 자동으로 깨끗한 쪽만 남음
- [app/label_detect.py](app/label_detect.py) 신규 작성: `find_label_y_positions`(OCR로 "10"·"30" y좌표 찾기) + `refine_y_range`("10"~"30" 사이 실측 간격으로 피치를 구하고, 위아래로 그 0.75배만큼 여유를 둬서 최종 세로 범위 계산). 라벨을 못 찾으면 `LabelsNotFoundError`
- [app/roi.py](app/roi.py) 갱신: `Y_RANGE`(고정값)는 이제 최종값이 아니라 "가로 레일 검출을 어느 대역에서 할지 정하는 대략적인 시작점"으로 격하됨. 순서: ①`Y_RANGE`로 대략 자른 밴드에서 가로(x1,x2) 찾기 → ②그 x1,x2 폭으로 OCR 돌려서 진짜 세로 범위(y1,y2) 계산 → ③최종 크롭. OCR 실패 시 `Y_RANGE`를 그대로 씀(예비값)
- 부작용 하나 발견·수정: 크롭 높이가 살짝 달라지면서, `basic_board.jpg`에서 숫자 라벨 잡음 그룹의 크기가 우연히 열 최소 인정 기준(`_MIN_COL_GROUP_SIZE=10`)을 넘어버려서 "열이 15개"로 깨짐. 실제 열의 최소 개수(실측 15개 이상)와 라벨 잡음(실측 최대 10개)이 아슬아슬하게 겹쳐 있었던 것 — 기준을 13으로 올려서 여유를 둠 ([app/board_detect.py](app/board_detect.py))
- 검증: `basic_board.jpg`/`board1.jpg`/`board2.jpg` 세 장 다 `roi.crop_to_roi()` → `board_detect.find_pinhole_pixels()` → `main.run_inference()`까지 끝까지 정상 동작. `board2.jpg`는 이제 "30" 라벨과 마지막 행이 크롭 안에 완전히 들어오고, U0/U13이 정확히 그 행에 찍힘
- `requirements.txt`에 `pytesseract` 추가. Tesseract 엔진 자체는 pip으로 안 깔리는 시스템 의존성이라 README에 별도 설치 안내 추가
- 교훈: "카메라·지그가 고정이니 세로는 고정값으로 충분하다"는 가정은, 실제로는 **레퍼런스가 있는지(라벨을 읽는지) 없이는 검증할 방법이 없는 가정**이었다. 사진 두 장만으로 "맞다"고 확인했던 것도 사실은 우연히 맞아떨어진 것이었고, 세 번째 사진에서 바로 깨짐 — 고정값 튜닝은 "지금 가진 샘플에서 맞는다"이지 "항상 맞는다"가 아니라는 걸 재확인함

### 사용자 요청: 90도 회전이 완벽한 수직을 보장하지 않을 수 있음 — 미세 기울기 보정(deskew) 추가

- 사용자: "완벽함. 혹시 처음에 이미지 받았을 때 90도로 돌리는 거 말고 브레드보드 세로 선이 각도 0으로 오게 돌리는 거 가능? 무조건 90도로 돌리니까 세로가 조금 삐뚤어질 수도 있을 것 같아서."
- 맞는 지적이었음. 실측: 선택된 단위의 왼쪽(빨강)·오른쪽(파랑) 경계 레일 선 각각에서, 그 선을 이루는 픽셀들로 `x = a*y + b` 직선을 최소제곱으로 피팅해서 실제 기울기(도)를 측정해봄
  - `basic_board.jpg`: 약 -0.48도, `board1.jpg`: 약 +0.02도(거의 없음), `board2.jpg`: 약 +1.23도 — 사진마다 실제로 카메라 장착 각도가 미묘하게 다름을 확인
  - 추가로 확인: **사진 전체 폭에서 레일 선마다 각도가 조금씩 달랐다** (예: `basic_board.jpg`에서 왼쪽 끝 레일은 -0.99도, 오른쪽 끝 레일은 -0.25도). 렌즈 왜곡/원근 때문으로 보임. 그래서 사진 전체의 평균 각도가 아니라, **우리가 실제로 쓸 단위의 두 경계선만으로** 각도를 잰다 (`rail_detect.measure_tilt_angle`) — 그래야 그 단위 안에서 정확하다
- [app/rail_detect.py](app/rail_detect.py)에 `_line_angle`(레일 선 하나의 기울기 측정) + `measure_tilt_angle`(선택된 단위의 두 경계선 각도 평균) 추가
- [app/roi.py](app/roi.py) 갱신: 90도 회전 → (기존과 동일하게) 대략적인 Y_RANGE 밴드에서 가로(x1,x2) 찾기 → **그 x1,x2로 기울기 측정 후 미세 회전(deskew)** → 회전했으니 가로(x1,x2) 다시 찾기 → 이후 OCR 세로 범위 계산은 기존과 동일. `_rotate_by_angle` 헬퍼로 `cv2.getRotationMatrix2D` + `warpAffine` 사용
- **부호 실수 한 번 함**: 측정한 각도를 그대로 회전에 넣었더니 기울기가 오히려 2배로 커짐(`basic_board.jpg`: -0.48도 → -0.95도). `cv2.getRotationMatrix2D`는 양수 각도가 반시계 방향이라, 측정된 기울기(시계 방향 양수로 정의)를 상쇄하려면 부호를 반대로(`-angle`) 줘야 했음. 부호 반대로 하니 세 사진 다 보정 후 잔여 각도가 0.03도 이내로 줄어드는 것으로 검증함
- 효과 확인: 핀홀 위치 평면 피팅(`_fit_row_plane`)의 x축 기울기 계수(`b2`, "같은 행이라도 x에 따라 y가 얼마나 변하는지")가, deskew 적용 전엔 사진 전체 폭 기준 최대 ~24px였는데 적용 후엔 최대 ~10px로 줄어듦 (`board2.jpg`는 -24px→-0.4px로 거의 완전히 사라짐). 완전히 0은 아닌데, 각도 측정 자체가 레일 선 폭 15px 구간만 보고 재는 거라 그 정밀도 한계로 보이며, 홀 하나 크기(~50px)보다 훨씬 작아서 실사용엔 문제없는 수준
- 검증: 세 사진 다 `roi.crop_to_roi()` → `board_detect.find_pinhole_pixels()` → `dev_plot_pinholes.py` → `main.run_inference()`까지 다시 확인. 핀홀 정렬 그대로 정확함 (회귀 없음)

### `board3.jpg` 실측: 라벨 하나만 폰트가 달라도 OCR 전체가 실패하는 문제

- 사용자가 새 사진 `board3.jpg` 제공, 크롭해서 핀홀 보여줬는데 사용자가 바로 지적: "board3 크롭 잘못됐는데.. 30이 안 보이잖아"
- 원인 확인: `label_detect.find_label_y_positions`가 "30"을 못 찾아서 `LabelsNotFoundError` 발생 → `roi.crop_to_roi`가 조용히 예비 고정값(`Y_RANGE`)으로 대체 → `board2.jpg` 때와 똑같은 방식으로 다시 잘림
- "30"을 못 찾은 이유를 실제로 파봄: OCR 검색 범위를 훨씬 넓혀도(±900px) "30"이 전혀 안 잡힘. 크롭 없이 원본에서 그 위치를 직접 잘라서 확대해보니 — **"30" 텍스트가 실제로 거기 있었다.** 다만 이 라벨만 **필기체 스타일(3과 0이 이어진 폰트)**로 인쇄돼 있어서 Tesseract가 숫자로 전혀 인식 못 함 (psm, 확대, 이진화 다 시도해봐도 안 됨). 같은 보드의 "10"/"15"/"20"/"25"는 전부 일반 폰트라 신뢰도 88~96으로 잘 읽혔음
- 즉 "라벨 하나가 있어야 계산 가능"이라는 기존 설계(`"10"`과 `"30"` 둘 다 필수)가 너무 깨지기 쉬웠음 — 라벨 5개(10,15,20,25,30) 중 단 하나만 폰트가 달라도 전체가 예비 고정값으로 후퇴해버림
- 수정 ([app/label_detect.py](app/label_detect.py) 전면 재작성):
  - "10"뿐 아니라 10/15/20/25/30 **다섯 라벨 전부**를 검색 대상으로 함 (`_LABEL_ROW_INDEX`: 각 라벨 → 물리적 행 인덱스 0/5/10/15/20)
  - **찾은 라벨이 2개 이상**이면 (행 인덱스, y) 점들로 `y = pitch*행인덱스 + intercept` 선형회귀를 해서 피치·기준점을 구함 — 꼭 10과 30일 필요 없이 아무 조합이나 됨
  - **1개만 찾히면** 기본 피치 추정값(`_DEFAULT_PITCH = 54.5`, 지금까지 실측한 사진들의 평균)으로 나머지를 외삽
  - **0개면** 기존처럼 `LabelsNotFoundError` → `roi.py`가 고정값으로 대체 (최후의 예비값은 유지)
- 검증: `board3.jpg`가 "10/15/20/25" 4개만으로 정확한 세로 범위를 계산해서, "30"(필기체라 OCR로는 못 읽은 라벨)까지 포함한 전체 행이 크롭 안에 제대로 들어옴. `basic_board.jpg`/`board1.jpg`/`board2.jpg` 세 장도 회귀 없이 그대로 정확함. 네 사진 다 `main.run_inference()`까지 정상 동작 확인
- 교훈: "필요한 조건 2개 중 하나가 없으면 전부 실패" 같은 설계는, 그 2개가 **서로 독립적으로 실패할 수 있는 이유**(여기선 서로 다른 라벨의 폰트 차이)가 있으면 특히 취약하다. 가진 정보(여기선 라벨 5개 중 일부)를 최대한 활용해서 등급을 낮춰가며(2개 이상 → 회귀, 1개 → 외삽, 0개 → 예비값) 대응하는 게 더 튼튼함
