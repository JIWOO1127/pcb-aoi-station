  - 열 구조: 0·1 = 왼쪽 전원 레일, 2~6 = 왼쪽 단자부, 7~11 = 오른쪽 단자부, 12·13 = 오른쪽 전원 레일

  - (처음엔 행/열을 반대로 짰다가 — 즉 글자를 열, 숫자를 행으로 — 사용자가 좌표표 이미지를 보내줘서 바로잡음)
  - **미해결**: YOLO 박스의 "픽셀 좌표" → 이 "그리드 좌표(row_index, col_index)"로 바꾸는 보정(calibration) 단계가 아직 없음. 스테이션이 기준 마크로 정렬해서 보내지만 촬영마다 핀홀 픽셀 위치가 미묘하게 달라서, 고정 픽셀 원점/간격을 하드코딩할 수 없음. 이미지별로 기준 마크(또는 핀홀 자체)를 다시 검출해서 homography/스케일을 계산하는 단계 필요. (물리적 핀홀 간격은 실제 브레드보드와 동일한 2.54mm 피치)

### 머신비전 구성 개념 정리

무엇이 딥러닝이고 무엇이 규칙 기반(전통적 이미지 처리)인지 헷갈리지 않도록 정리:

- **딥러닝**: YOLO 객체 탐지 — 이미지에서 부품 종류·위치(박스)·신뢰도를 검출. (`detect_parts`, 아직 미구현)
- **전통적 머신비전(규칙 기반)**: 기준 마크/핀홀 자체를 찾는 것, 원근 보정(homography)으로 픽셀 → 그리드 좌표 변환. (`find_board_corners`, `calibration.py`)
- **후처리(순수 계산)**: YOLO 박스와 핀홀 위치를 대조해서 "어느 핀홀이 가려졌는지" 구조화 (`board.py`), 그리드 좌표를 실제 존재하는 핀홀 라벨로 스냅 (`pinhole_grid.snap_to_pinhole`)
- **FastAPI**: 머신비전 모델이 아니라, C# 스테이션과 Python 추론 코드를 연결하는 API 서버일 뿐
- **PASS/FAIL 판정**: 딥러닝도 이 서비스도 아니고, C# 스테이션의 규칙 엔진이 담당

즉 "브레드보드 구조화" 전체가 머신비전 작업이긴 하지만, 그 안에서도 딥러닝(부품 인식)과 기하학/OpenCV(좌표 변환)와 순수 후처리(구조화)가 나뉘어 있다. 나중에 모델이 핀홀·단자 키포인트까지 직접 검출하도록 학습시키면 그 부분도 딥러닝이 되겠지만, 검출 좌표를 핀홀 이름으로 바꾸는 마지막 단계는 그래도 규칙 기반으로 남을 수 있다.

### 자동 보드 크롭·홀 좌표 표시를 위한 대안 검토

- 코드 변경 없이 개념만 검토함.
- 딥러닝을 쓰는 권장 방식: `YOLO-Pose` 같은 키포인트 모델이 보드와 네 모서리 핀홀(A0, A13, U0, U13)을 검출한다.
- 검출한 네 점으로 homography를 계산해 보드를 표준 크기로 원근 보정·크롭하고, 알려진 A~U/0~13 격자를 이미지 위에 투영한다.
- 이 방식에서 보드/모서리 검출은 딥러닝이고, 크롭·원근 보정·홀 좌표 표시는 기하학적 후처리다.
- 대안으로 `YOLO-Seg`/Mask R-CNN을 이용해 보드 외곽 마스크를 찾을 수 있으며, 모든 핀홀을 직접 검출하는 모델은 가림과 라벨링 비용 때문에 우선순위가 낮다.
- 카메라와 지그가 고정되고 보드에 표식을 붙일 수 있다면 ArUco/AprilTag가 딥러닝보다 간단하고 안정적인 선택이다.
- 실제 요구사항은 큰 보드 전체가 아니라 가운데의 검사 대상 구역만 크롭하는 것임. 따라서 전체 보드 네 모서리 검출보다 2단계 coarse-to-fine 방식이 적합하다.
- 1단계: 축소한 전체 이미지에서 YOLO-OBB/YOLO-Seg 등으로 검사 대상 구역을 찾는다. 2단계: 검출 좌표로 원본 고해상도 이미지를 크롭하고, 크롭 내부의 로컬 기준점 또는 레일/핀홀 격자로 homography를 계산한다.
- 크롭 안에 전체 보드 모서리가 없다면 A0/A13/U0/U13을 전체 보드 모서리로 찾는 방식은 사용할 수 없다. 검사 구역 주변에 로컬 기준 마크를 두거나, 레일과 반복 핀홀 격자를 검출해 좌표 기준을 복원해야 한다.
- 제공된 실제 사진은 동일한 브레드보드 단위가 가로로 연속된 구조다. 각 단위의 빨강/파랑 전원 레일이 비교적 뚜렷하므로, 모든 단위 후보를 검출한 뒤 중심점이 이미지 중심에 가장 가까운 단위를 선택해 크롭하는 방식이 가능하다.
- 고정 환경에서는 레일 색상 검출 + 중심 단위 선택이 가장 단순하다. 조명·기울기 변화가 크면 YOLO-OBB/YOLO-Seg로 각 단위의 사각형/마스크를 검출하고 중심 단위를 고른 뒤, YOLO-Pose 또는 로컬 기준점으로 원근 보정한다.
- 반복 무늬만으로는 어느 단위가 검사 대상인지 의미적으로 구분할 수 없으므로, `화면 중심에 가장 가까운 단위`, `왼쪽에서 N번째 단위` 같은 선택 규칙이나 별도 마커가 필요하다.

### 스테이션과 핀홀 값으로 통신하는 이유

- 픽셀 좌표는 카메라 해상도, 크롭 위치, 거리, 기울기와 원근에 따라 매 촬영마다 바뀌지만 `J9` 같은 핀홀 라벨은 물리적 위치를 나타내므로 안정적이다.
- 추론 서비스가 영상 좌표 보정 책임을 맡고, C# 스테이션은 카메라 세부사항 없이 레시피의 기대 핀홀과 실제 핀홀을 직접 비교할 수 있다.
- 핀홀 라벨은 사람이 읽고 로그·DB·오류 화면에서 추적하기 쉽고, API 데이터도 단순해진다.
- 픽셀은 추론 서비스 내부 계산과 디버깅에 계속 사용되며, 최종 API 경계에서 도메인 좌표인 핀홀 값으로 변환한다.
- 단점은 보정이 틀리면 잘못된 핀홀로 양자화될 수 있다는 점이므로 신뢰도와 필요시 디버그용 픽셀 박스를 별도로 보존하는 것이 좋다.

### 이미지 전처리 파일 역할 요약

- `app/roi.py`: JPEG 디코딩 이후 이미지를 90도 회전하고, 중앙 검사 단위를 선택하며, 레일 기울기를 보정한 뒤 최종 ROI를 크롭한다.
- `app/rail_detect.py`: HSV 색상 임계값으로 빨강·파랑 전원 레일을 검출하고 단위 보드 후보, 중앙 단위의 x범위, 레일 기울기를 계산한다.
- `app/label_detect.py`: Tesseract OCR로 인쇄된 `10/15/20/25/30` 라벨을 찾아 A~U가 들어갈 세로 y범위를 계산한다.
- `app/board_detect.py`: 크롭 영상에서 어두운 사각형 홀 blob을 찾고 14개 열을 구성한 뒤, 전체 홀로 행 평면을 피팅하여 282개 핀홀의 실제 픽셀 위치를 계산한다.
- `app/pinhole_grid.py`: A~U, 0~13과 E/K/Q 전원 레일 누락 규칙을 정의하고 유효 핀홀 라벨을 제공한다.
- `app/board.py`: 계산된 홀을 객체로 구성하고 향후 YOLO 부품 박스와 겹치는 홀을 매칭한다. 전처리보다는 구조화·후처리에 해당한다.
- `app/calibration.py`: 네 모서리 homography 방식의 레거시 보정 코드이며, 실제 열 간격과 렌즈 왜곡 문제 때문에 현재 기본 경로는 `board_detect.py`다.
- `app/dev_plot_pinholes.py`: 검출한 핀홀을 이미지에 그려 결과를 눈으로 확인하는 개발용 도구다.
- `app/main.py`: 전체 흐름을 연결한다. 이미지 디코딩 → ROI 크롭 → 282개 홀 위치 계산 → YOLO 탐지(TODO) → 홀/박스 매칭 → API 응답 순서다.

### Homography 개념

- Homography는 같은 평면을 서로 다른 시점에서 본 두 좌표계 사이를 연결하는 3×3 원근변환 행렬이다.
- 보드의 네 대응점(예: A0, A13, U0, U13)을 알면 비스듬한 사진의 픽셀 좌표를 정면 그리드 좌표로 변환하거나 반대로 그리드 좌표를 이미지에 투영할 수 있다.
- 원근과 회전은 보정할 수 있지만 렌즈 왜곡, 휘어진 표면, 잘못된 기준점은 하나의 Homography만으로 해결할 수 없다.
- 현재 `calibration.py`는 네 모서리와 균등 열 간격을 가정한 레거시 방식이며, 실제 브레드보드 중앙 채널과 렌즈 왜곡 때문에 기본 경로는 홀을 직접 검출하는 `board_detect.py`를 사용한다.

### 현재 ROI 크롭 순서

- `main._decode_image()`가 JPEG 바이트를 OpenCV BGR 이미지로 변환한다.
- `roi.crop_to_roi()`가 카메라 방향을 맞추기 위해 먼저 반시계 방향으로 90도 회전한다.
- 대략적인 세로 구간 `Y_RANGE=(646, 1818)`에서 `rail_detect.find_center_unit_x_range()`가 HSV 색상으로 빨강·파랑 레일을 찾아 여러 단위 후보 중 프레임 중앙에 가장 가까운 단위를 선택한다. 실패 시 `FALLBACK_X_RANGE=(1350, 2630)`을 쓴다.
- 선택된 양쪽 레일의 기울기를 선형회귀로 측정해 이미지를 미세 회전(deskew)하고, 회전 후 레일 x범위를 다시 검출한다.
- `label_detect.refine_y_range()`가 Tesseract OCR로 `10/15/20/25/30` 라벨을 찾아 A~U의 세로 범위를 계산한다. 2개 이상이면 선형회귀, 1개면 기본 피치 54.5px로 외삽하며, 실패하면 고정 `Y_RANGE`를 쓴다.
- 최종적으로 `rotated[y1:y2, x1:x2]`를 반환한다. 현재 크롭은 딥러닝이 아니라 색상 검출·선형회귀·OCR 기반이다.
- README에 현재 크롭 방식의 설계 이유를 추가했다. 검사 지그와 카메라가 고정되어 검사 대상과 대략적인 범위가 정해져 있으므로 범용 보드 검출 대신 고정 범위를 기준으로 사용하고, 실제 레일·라벨 검출로 촬영마다 생기는 작은 위치·기울기·크기 차이만 보정한다는 원칙을 명시했다.

### 저화질 입력에 대한 한계

- 현재 전처리 파라미터는 약 `1280×1172` 크롭 영상과 행 피치 약 `54.5px`에 맞춰져 있어 임의의 저해상도 입력에 스케일 불변이 아니다.
- 레일 색상 검출은 선의 색과 두께가 남아 있으면 비교적 견디지만, 작은 숫자를 읽는 OCR과 어두운 사각 홀 blob 검출이 먼저 불안정해진다.
- `board_detect.py`의 blob 면적, 열 그룹 간격, 행 피치 허용값(`35~70px`)이 고정 픽셀 값이므로 절반 크기 영상에서는 그대로 실패할 가능성이 높다.
- 권장 방식은 원본 고해상도에서 크롭·홀 좌표 계산을 수행하고, YOLO 입력만 별도로 리사이즈하는 것이다.
- 반드시 저해상도를 지원해야 한다면 기준 해상도로 업스케일한 뒤 OCR을 수행하거나, 모든 임계값을 이미지 크기/추정 피치 비율로 바꾸고 여러 해상도에서 검증해야 한다.

### 휴대폰 실시간 카메라 연결

- 프로젝트 README의 설계대로 휴대폰 카메라를 Windows PC에 전달할 때는 Camo Camera(휴대폰)와 Camo Studio(PC)를 사용할 수 있다.

- 연결 후 Windows에는 `Camo Camera`라는 가상 웹캠으로 나타나며, 추후 OpenCV에서 카메라 장치로 열어 프레임을 받을 수 있다.

- Camo 영상이 저화질로 들어오는 문제가 확인됨. Camo 무료판은 1080p 이상이 잠겨 있을 수 있고, Camo가 고해상도를 제공해도 영상을 받는 프로그램이 640×480 또는 720p를 요청하면 실제 프레임은 낮은 해상도로 들어올 수 있다.
- 현재 전처리는 4032×3024 원본 사진과 약 1280×1172 크롭을 기준으로 검증돼 있어 720p 웹캠 스트림을 그대로 쓰면 OCR·핀홀 검출 임계값이 맞지 않을 가능성이 크다.
- AOI 권장 구조는 저해상도 실시간 스트림은 위치 확인용으로만 쓰고, 검사 트리거 시 휴대폰이 원본 해상도 JPEG 한 장을 촬영해 PC로 전송하는 방식이다. Camo를 계속 쓰려면 1080p/4K 프로필, USB 직접 연결, 후면 메인 렌즈, 디지털 줌·배경 효과 해제, 수신 프로그램의 요청 해상도를 함께 확인해야 한다.

### 가로 크롭 선택 기준: "부품 있는 쪽" → "프레임 중앙" 으로 변경

- 사용자 확인: 테스트 사진(여러 보드가 나란히 찍힌 것) 중 실제 검사 대상은 **가운데 보드**였음. `find_populated_unit_x_range`(edge 밀도로 부품 많은 쪽 선택)는 부품이 적은 진짜 대상 대신 부품 많은 다른 보드를 골라서 틀렸음
- 이유: 실제 검사 라인은 카메라·지그가 고정이라, 검사 대상 보드는 항상 프레임의 같은(중앙 부근) 위치에 놓인다. "부품이 많아 보이는 곳"보다 "위치가 중앙인 곳"이 부품 개수·조명에 안 흔들리는 더 안정적인 기준
- [app/rail_detect.py](app/rail_detect.py)에 `find_center_unit_x_range` 추가: 후보 단위들 중 중심 x좌표가 프레임 중앙에 가장 가까운 것을 선택. `find_populated_unit_x_range`는 남겨뒀지만 기본값에서 제외
- [app/roi.py](app/roi.py): `crop_to_roi`가 `find_center_unit_x_range`를 쓰도록 변경
- 검증(`basic_board.jpg`): 후보 2개 중 edge 밀도가 낮은(부품 거의 없는) 쪽이 프레임 중앙에 더 가까워서 선택됨 → 사용자가 원하던 가운데 보드와 일치

### 원근 펼치기 도입 + calibration.py 설계 결함 발견

- 크롭된 이미지가 살짝 기울어져 있어서(카메라 각도), 축 정렬된 사각형 크롭이 왼쪽·오른쪽에서 다른 높이를 잘라 오른쪽 상단 핀홀이 살짝 잘리는 게 눈에 띔
- 네 모서리 핀홀(A0/A13/U0/U13)을 홀 blob 검출로 찾은 뒤 `cv2.getPerspectiveTransform` + `warpPerspective`로 평면처럼 펴봄(원근 펼치기) → 확실히 더 정확해짐 (좌우 레일이 같은 높이로 맞춰짐)
- 이 과정에서 `calibration.py`의 근본적인 한계를 실측으로 발견함: **이 브레드보드는 열 6과 7 사이에 단자부 채널(물리적으로 넓은 갭)이 있어서 열 간격이 균등하지 않은데, `calibration.py`는 네 모서리(열 0·13)만으로 호모그래피를 계산해서 열 인덱스(0~13)가 균등한 간격이라고 가정한다.** 같은 네 모서리로 `calibration.py`를 그대로 돌려보니, 갭을 지나면서 오차가 누적돼서 원근 펼치기 전보다도 부정확했음
- 결론: **기울기(회전)는 호모그래피로 보정할 수 있지만, 열 간격의 비균등성은 호모그래피 하나로 표현 못 하는 별개의 문제.** 열 간격은 실제로 검출한 값을 써야 함
- [app/board_detect.py](app/board_detect.py) 신규 작성 — 정확도가 확인된 방식을 정식 모듈로 formalize:
  1. `_find_hole_centroids`: 홀 blob 전부 검출 (기존 dev 스크립트 로직을 정리)
  2. `_pick_extreme_corners`: 볼록 사각형 꼭짓점 성질(x+y, -x+y, x-y, -x-y 최소화)로 네 모서리 자동 선택
  3. `_flatten`: 네 모서리로 원근 변환해서 기울기만 보정 (열 간격 보간에는 안 씀)
  4. `_fit_grid`: 평탄화된 이미지에서 다시 홀 검출 → 열은 실제 k-means 클러스터 x좌표 그대로 사용(비균등 간격 보존), 행은 물리적으로 균등하므로 첫/끝 행 중심 사이를 선형보간
  5. `find_pinhole_pixels(image)`: 위 전부를 묶어서 `{라벨: (x,y)}` 282개 + 평탄화된 이미지 반환
- [app/board.py](app/board.py)에 `all_holes_from_image(image)` 추가 (board_detect 기반, 권장 경로). 기존 `all_holes(calibration)`은 레거시로 남김
- [app/main.py](app/main.py) `run_inference` 갱신: `find_board_corners`(TODO였던 것) 제거하고 `board.all_holes_from_image(roi_image)`로 대체 → **`find_board_corners` TODO 해소**. `detect_parts`는 이제 평탄화된 이미지를 받도록 변경 (YOLO도 평탄화된 좌표계 기준으로 돌아야 함)
- [app/calibration.py](app/calibration.py) 문서에 위 한계 명시, 레거시로 표시
- [app/dev_plot_pinholes.py](app/dev_plot_pinholes.py): 시각 확인용 스크립트를 `board_detect.py` 기반으로 재작성 (중복 로직 제거)
- 검증: `basic_board.jpg`(부품 적음)와 `board1.jpg`(IC·LED·저항·커패시터 등 부품 많음) 둘 다 실제 파이프라인(`roi.crop_to_roi` → `board.all_holes_from_image`)으로 끝까지 돌려서 핀홀 정렬 확인 — 부품에 가려진 홀도 포함해서 정렬 잘 유지됨
- 남은 TODO는 이제 `detect_parts`(YOLO) 하나뿐 — README.md TODO 섹션 갱신함

### 원근 펼치기 결국 제거 — board1에서 오히려 왜곡 증가 확인됨

- 위에서 도입한 원근 펼치기를 `board1.jpg`(부품 많은 사진)에 적용해보니, 사용자가 직접 확인: **`board1_flattened.jpg`가 `board1_cropped.jpg`(안 편 원본)보다 더 왜곡돼 있고, 그래서 `board1_pinholes`가 실제 홀 위치와 안 맞음**
- 실측으로 원인 확인: 안 편 원본 크롭에서 행 A(맨 윗줄)의 실제 y좌표가 열마다 36.5~52px 사이에서 완만하게 처져 있었음(렌즈 왜곡으로 보임). 그런데 네 모서리짜리 호모그래피는 이 처짐을 "두 끝점을 잇는 직선"으로 가정해서 억지로 펴려다 보니, 평탄화 후에는 오히려 7~50px까지 더 크게 출렁이는 걸 확인함 (호모그래피는 원근/기울기는 고칠 수 있어도, 렌즈 왜곡 같은 비선형 곡률은 못 고치고 오히려 증폭시킬 수 있음)
- 게다가 행 y좌표를 모든 열을 합쳐서 한 번에 전역 k-means로 구했던 것도 이 왜곡을 더 섞이게 만든 원인이었음
- **결론 및 조치**: 원근 변환(perspective warp)을 완전히 제거함. [app/board_detect.py](app/board_detect.py)를 다시 작성해서, 이미지를 펴지 않고 **열마다 독립적으로** 그 열 자신의 첫 홀~마지막 홀 사이를 선형보간하도록 변경 (열 사이 기울기 차이가 있어도 이미지 변형 없이 그대로 반영됨). `find_pinhole_pixels`가 반환하는 `image`는 이제 입력과 동일함(변형 없음) — `board.py`, `main.py`도 이에 맞춰 갱신 (더 이상 "평탄화된 이미지"라는 개념이 없음)
- 이 과정에서 **열 검출(`_fit_columns`) 자체의 버그도 하나 더 발견**: 처음엔 x좌표에 k=14 고정 k-means를 썼는데, 보드 실크스크린에 인쇄된 행 번호 숫자("10","15","20",...)가 어두운 blob으로 오검출돼서 노이즈로 섞여 들어가면, 근처 실제 열의 k-means 중심이 최대 13px까지 밀리는 걸 확인함 (`basic_board`의 열 11이 867.4로 밀렸던 것 — 실제로는 853.5가 맞음). 숫자 라벨은 실제 열보다 검출 개수가 훨씬 적다는 점(전체 21행 중 1~2곳에서만 나타남)을 이용해서, k-means 대신 **x좌표 정렬 후 간격 기반 그룹핑**(`rail_detect.py`의 레일선 클러스터링과 같은 원리) + 그룹 크기가 너무 작으면(<10) 잡음으로 버리는 방식으로 교체함. 두 사진 모두 정확히 14열이 검출되는 것으로 검증함
- 결과물 이름도 정리: `*_flattened.jpg`는 더 이상 안 만들고, `basic_board_pinholes.jpg`/`board1_pinholes.jpg`로 통일
- 교훈: 어떤 보정 기법(원근 변환 등)이 "이론적으로 맞아 보인다"고 해서 실제로 더 정확해지는 건 아니다 — 반드시 다른 사진(특히 더 복잡한/노이즈 많은 사진)으로도 실측 비교해야 함. `basic_board.jpg`(단순한 사진) 하나만으로 좋아 보였던 방법이 `board1.jpg`(복잡한 사진)에서 깨진 사례

### 진짜 원인 발견: 레일 열 보간 계산 자체가 틀렸었다 (렌즈 왜곡 아님)

- 위 수정 후에도 사용자가 `board1.jpg`에서 여전히 핀홀이 안 맞는다고 확인 (오른쪽 레일 열 쪽, "10" 라벨 위 핀홀들이 눈에 띄게 어긋남). 처음엔 "렌즈 왜곡 때문에 열 안에서도 피치가 변한다"고 오판했었는데, 실측해보니 **훨씬 단순하고 결정론적인 버그**였음
- 원인: 레일 열(0,1,12,13)은 E/K/Q 행이 빠져서 `expected_rows`가 18개뿐인데, 코드가 `np.linspace(첫홀, 마지막홀, len(expected_rows))`로 **"17칸 균등 간격"**으로 나눴음. 그런데 실제로는 D→F, J→L, P→R 사이가 (건너뛴 E/K/Q 자리만큼) 물리적으로 2칸 너비라서, 진짜 물리적 간격은 20칸임. 이 불일치 때문에 매 칸마다 조금씩 어긋난 게 누적되어, 레일 열 아래로 갈수록 점점 크게 밀렸던 것. (단자부 열 2~11은 21행이 다 있어서 이 버그의 영향이 전혀 없었고, 그래서 가운데는 항상 잘 맞아 보였던 것도 이걸로 설명됨)
- 수정 ([app/board_detect.py](app/board_detect.py) `find_pinhole_pixels`): `expected_rows` 안에서의 순번이 아니라, `pinhole_grid.ROWS`(A~U, 21개) 안에서의 **진짜 물리적 인덱스**를 기준으로 보간하도록 변경. 구체적으로 `np.linspace(첫홀, 마지막홀, 21)`로 21칸 전체를 만든 다음, 각 행 글자의 실제 인덱스(E=4,K=10,Q=16 스킵)로 값을 골라 쓰는 방식
- 검증: `board1.jpg`의 A13 쪽 레일 열에서 재확인 — 수정 전엔 맨 위 모서리(A13)에 실제 홀이 안 보이고 그 아래 점들도 계속 한 칸씩 밀려 보였는데, 수정 후엔 모든 행에서 정확히 홀 중앙에 점이 찍힘. `basic_board.jpg`도 재확인 완료, 두 사진 다 레일 열까지 포함해서 정확히 맞음
- 교훈: "이 사진에선 잘 맞아 보인다"가 아니라, **실제 계산 로직을 손으로 다시 검산**해야 하는 종류의 버그였음. 특히 이번처럼 "칸 개수로 나누기" 같은 계산은 물리적 구조(스킵된 행 등)를 다시 한번 명시적으로 확인해야 함
- 사용자가 함께 물어본 것: "YOLO-OBB/YOLO-Seg를 쓰는 게 나을까?" → 답변: OBB/Seg는 "이 보드가 어디 있는지"(바운딩박스/마스크) 찾는 모델이라 지금 겪는 문제(핀홀 282개의 서브픽셀 정확한 위치)와는 결이 다름. 이 문제에 맞는 딥러닝 도구는 키포인트 검출(YOLO-Pose류)이지만, 핀홀 위치를 라벨링한 학습 데이터가 아직 없어서 투자 비용이 큼. 이번 버그는 순수 계산 오류였고 고치고 나니 실측 사진 2장 모두 완벽히 맞아서, 지금 시점에 딥러닝 전환의 필요성은 낮다고 판단 — README.md에도 같은 결론 정리함

### 두 번째 실제 버그: 열마다 "여분의 홀"이 낄 수 있다는 걸 놓침

- 사용자가 위 수정 후에도 재확인: "오른쪽으로 가면 왜곡 생기잖아. 오른쪽 숫자 10 라인의 가장 오른쪽 핀이 A13인데 그 윗줄 핀홀까지 보여." → `board1.jpg`를 다시 실측
- 원인: 카메라가 살짝 기울어져 있어서, 고정 `Y_RANGE`로 자른 크롭의 위쪽 경계가 열마다 다른 실제 행에서 잘림. 오른쪽 4개 열(10,11,12,13, 즉 두 번째 단자부 오른쪽 절반 + 오른쪽 레일)은 크롭에 **행 A보다 한 칸 위의 진짜 홀이 하나 더 딸려 들어와 있었고**, 코드가 "이 열에서 검출된 제일 위 홀 = 행 A"라고 가정했기 때문에 이 여분의 홀을 A로 잘못 인식해서 그 아래 전체가 한 칸씩 밀렸음. (왼쪽 10개 열은 이 여분의 홀이 없어서 멀쩡했음 — 그래서 왼쪽은 계속 잘 맞아 보였던 것)
- 수정 ([app/board_detect.py](app/board_detect.py) `find_pinhole_pixels`): 전역 칸 간격(피치)을 모든 열의 실측 간격(중복 제거 후, 35~70px 범위만 필터링)에서 median으로 추정한 다음, 열마다 **반대쪽 끝(신뢰할 수 있는 쪽) + 전역 피치로 "진짜 행 A/U가 있어야 할 위치"를 역산**해서 그 범위를 벗어난 여분의 홀은 걸러내고 나서 보간하도록 변경. 중첩 컨투어(같은 홀이 두 번 검출되는 것)를 먼저 합치는 `_dedup`도 추가함
- 검증: `board1.jpg`의 A13이 이제 왼쪽 A0와 정확히 같은 높이(진짜 행 A)에 찍힘, 그 아래 전체 열도 실제 홀과 정확히 일치. `basic_board.jpg`는 원래 이 문제가 없었고 회귀도 없음을 재확인
- 교훈: "카메라·지그가 고정이라 세로 크롭도 고정값으로 충분하다"는 가정이 실제로는 미묘한 기울기 하나로 깨질 수 있다는 걸 두 번째로 확인함(첫 번째는 가로 크롭 때). 다만 이번엔 크롭 자체를 고치는 대신(카메라마다 다시 튜닝해야 해서 비용이 큼), **알고리즘이 "크롭에 의도한 범위 밖 홀이 한두 개 더 있을 수 있다"는 걸 전제하고 스스로 걸러내도록** 만들어서 더 근본적으로 해결함

### 세 번째 실제 버그이자 진짜 근본 원인: "열마다 따로 계산"이 원천적으로 잘못된 설계였다

- 사용자가 위 수정 후에도 재확인하면서 결정적인 제약을 하나 알려줌: **"같은 알파벳(A~U)의 핀홀은 같은 직선상에 있어야 한다."** 실측 사진에 분홍색으로 진짜 U13 위치를 표시해서 보내줌 — 우리가 찍은 점과 어긋나 있었음
- 이 제약을 듣고 나서야 설계 결함을 깨달음: 그동안 "열마다 따로" 그 열 자신의 첫 홀~마지막 홀 사이를 선형보간해왔는데, 이러면 **열 A의 보간 결과와 열 B의 보간 결과가 서로 다른 열에서 계산되기 때문에, 같은 행(예: K행)이라도 열마다 y값이 조금씩 달라질 수 있음** — 이게 "같은 행은 일직선이어야 한다"는 물리적 제약을 구조적으로 보장하지 못하는 원인이었음. `board1.jpg`에서 열 20번(K행 부근) 근처가 왼쪽은 멀쩡한데 오른쪽 몇 개 열에서만 15~20px 위로 어긋나 있던 것도 이 때문 — 렌즈 왜곡이 아니라, 열마다 독립적으로 계산한 결과가 우연히 그 지점에서 어긋난 것
- 수정 ([app/board_detect.py](app/board_detect.py) `_fit_row_plane`): 열마다 따로 계산하는 대신, **모든 열의 모든 홀을 한꺼번에 모아서 `y = b0 + b1*행번호 + b2*x` 평면 하나를 최소제곱으로 피팅**하도록 완전히 바꿈. 각 홀이 몇 번째 행인지는 그 열의 반대쪽 끝(신뢰할 수 있는 쪽) + 전역 피치로 역산해서 추정(이전 버그 수정 로직 재사용). 평면 하나로 모든 위치를 계산하므로, **같은 행번호는 정의상(수학적으로) 항상 일직선** — 열마다 다른 결과가 나올 수 없는 구조로 바뀜. 이상치(occlusion 등으로 잘못 매칭된 점)는 1차 피팅 후 잔차 15px 넘는 것만 제외하고 재피팅
- 검증: `board1.jpg`에서 이전에 어긋났던 지점(K행 부근 오른쪽 열들)까지 포함해서 전부 홀 중앙에 정확히 맞음. `basic_board.jpg`도 회귀 없음. 평면 피팅 잔차: 이상치 제거 전 표준편차 ~5.8px(최대 ~29px), 실사용에 충분히 정확
- 교훈: 데이터를 더 많이 실측하는 것보다, **사용자가 알려준 "물리적으로 당연한 제약"(같은 행은 일직선)을 알고리즘 설계에 명시적으로 반영하는 게 훨씬 근본적인 해결책**이었다. 열별 독립 계산은 "열마다 다를 수 있다"는 유연성이 오히려 이 제약을 깨는 자유도가 되어버렸음

### OCR(Tesseract)로 "10"·"30" 라벨을 읽어서 세로 크롭 범위 계산

- 환경 준비: `pytesseract`(pip) + Tesseract 엔진 실행파일이 별도로 필요함. `conda install -n pcb-aoi -c conda-forge tesseract`로 설치 (버전 5.5.3). Windows에서 conda-forge 패키지의 tessdata 경로가 실행파일 기준 기본 탐색 경로와 달라서 `TESSDATA_PREFIX` 환경변수를 명시적으로 잡아줘야 했음 — [app/label_detect.py](app/label_detect.py)가 `sys.executable`(현재 conda 환경의 python.exe) 기준으로 실행파일·tessdata 경로를 자동으로 찾아서 설정하도록 만듦(수동 환경변수 설정 불필요)
- 실측: 넓은 세로 범위(`roi.Y_RANGE` ±400px)에서 가로로 이미 찾은 유닛(x1~x2) 폭만큼만 OCR을 돌려보니, "10"·"15"·"20"·"25"·"30" 텍스트를 신뢰도(conf) 88~96으로 안정적으로 읽음. 왼쪽 라벨은 근처 홀과 겹쳐서 잡음이 섞였지만(`"158"`, `"308"` 등으로 오검출), 오른쪽 라벨은 깨끗하게 읽힘 — 그래서 신뢰도 임계값(80)으로 걸러내면 자동으로 깨끗한 쪽만 남음
- [app/label_detect.py](app/label_detect.py) 신규 작성: `find_label_y_positions`(OCR로 "10"·"30" y좌표 찾기) + `refine_y_range`("10"~"30" 사이 실측 간격으로 피치를 구하고, 위아래로 그 0.75배만큼 여유를 둬서 최종 세로 범위 계산). 라벨을 못 찾으면 `LabelsNotFoundError`

- 검증: `basic_board.jpg`/`board1.jpg`/`board2.jpg` 세 장 다 `roi.crop_to_roi()` → `board_detect.find_pinhole_pixels()` → `main.run_inference()`까지 끝까지 정상 동작. `board2.jpg`는 이제 "30" 라벨과 마지막 행이 크롭 안에 완전히 들어오고, U0/U13이 정확히 그 행에 찍힘

  - `basic_board.jpg`: 약 -0.48도, `board1.jpg`: 약 +0.02도(거의 없음), `board2.jpg`: 약 +1.23도 — 사진마다 실제로 카메라 장착 각도가 미묘하게 다름을 확인
  - 추가로 확인: **사진 전체 폭에서 레일 선마다 각도가 조금씩 달랐다** (예: `basic_board.jpg`에서 왼쪽 끝 레일은 -0.99도, 오른쪽 끝 레일은 -0.25도). 렌즈 왜곡/원근 때문으로 보임. 그래서 사진 전체의 평균 각도가 아니라, **우리가 실제로 쓸 단위의 두 경계선만으로** 각도를 잰다 (`rail_detect.measure_tilt_angle`) — 그래야 그 단위 안에서 정확하다
- [app/rail_detect.py](app/rail_detect.py)에 `_line_angle`(레일 선 하나의 기울기 측정) + `measure_tilt_angle`(선택된 단위의 두 경계선 각도 평균) 추가
- [app/roi.py](app/roi.py) 갱신: 90도 회전 → (기존과 동일하게) 대략적인 Y_RANGE 밴드에서 가로(x1,x2) 찾기 → **그 x1,x2로 기울기 측정 후 미세 회전(deskew)** → 회전했으니 가로(x1,x2) 다시 찾기 → 이후 OCR 세로 범위 계산은 기존과 동일. `_rotate_by_angle` 헬퍼로 `cv2.getRotationMatrix2D` + `warpAffine` 사용
- **부호 실수 한 번 함**: 측정한 각도를 그대로 회전에 넣었더니 기울기가 오히려 2배로 커짐(`basic_board.jpg`: -0.48도 → -0.95도). `cv2.getRotationMatrix2D`는 양수 각도가 반시계 방향이라, 측정된 기울기(시계 방향 양수로 정의)를 상쇄하려면 부호를 반대로(`-angle`) 줘야 했음. 부호 반대로 하니 세 사진 다 보정 후 잔여 각도가 0.03도 이내로 줄어드는 것으로 검증함
- 효과 확인: 핀홀 위치 평면 피팅(`_fit_row_plane`)의 x축 기울기 계수(`b2`, "같은 행이라도 x에 따라 y가 얼마나 변하는지")가, deskew 적용 전엔 사진 전체 폭 기준 최대 ~24px였는데 적용 후엔 최대 ~10px로 줄어듦 (`board2.jpg`는 -24px→-0.4px로 거의 완전히 사라짐). 완전히 0은 아닌데, 각도 측정 자체가 레일 선 폭 15px 구간만 보고 재는 거라 그 정밀도 한계로 보이며, 홀 하나 크기(~50px)보다 훨씬 작아서 실사용엔 문제없는 수준
- 검증: 세 사진 다 `roi.crop_to_roi()` → `board_detect.find_pinhole_pixels()` → `dev_plot_pinholes.py` → `main.run_inference()`까지 다시 확인. 핀홀 정렬 그대로 정확함 (회귀 없음)

### `board3.jpg` 실측: 라벨 하나만 폰트가 달라도 OCR 전체가 실패하는 문제

- 사용자가 새 사진 `board3.jpg` 제공, 크롭해서 핀홀 보여줬는데 사용자가 바로 지적: "board3 크롭 잘못됐는데.. 30이 안 보이잖아"
- 원인 확인: `label_detect.find_label_y_positions`가 "30"을 못 찾아서 `LabelsNotFoundError` 발생 → `roi.crop_to_roi`가 조용히 예비 고정값(`Y_RANGE`)으로 대체 → `board2.jpg` 때와 똑같은 방식으로 다시 잘림
- "30"을 못 찾은 이유를 실제로 파봄: OCR 검색 범위를 훨씬 넓혀도(±900px) "30"이 전혀 안 잡힘. 크롭 없이 원본에서 그 위치를 직접 잘라서 확대해보니 — **"30" 텍스트가 실제로 거기 있었다.** 다만 이 라벨만 **필기체 스타일(3과 0이 이어진 폰트)**로 인쇄돼 있어서 Tesseract가 숫자로 전혀 인식 못 함 (psm, 확대, 이진화 다 시도해봐도 안 됨). 같은 보드의 "10"/"15"/"20"/"25"는 전부 일반 폰트라 신뢰도 88~96으로 잘 읽혔음
- 즉 "라벨 하나가 있어야 계산 가능"이라는 기존 설계(`"10"`과 `"30"` 둘 다 필수)가 너무 깨지기 쉬웠음 — 라벨 5개(10,15,20,25,30) 중 단 하나만 폰트가 달라도 전체가 예비 고정값으로 후퇴해버림
- 수정 ([app/label_detect.py](app/label_detect.py) 전면 재작성):
  - "10"뿐 아니라 10/15/20/25/30 **다섯 라벨 전부**를 검색 대상으로 함 (`_LABEL_ROW_INDEX`: 각 라벨 → 물리적 행 인덱스 0/5/10/15/20)
  - **찾은 라벨이 2개 이상**이면 (행 인덱스, y) 점들로 `y = pitch*행인덱스 + intercept` 선형회귀를 해서 피치·기준점을 구함 — 꼭 10과 30일 필요 없이 아무 조합이나 됨
  - **1개만 찾히면** 기본 피치 추정값(`_DEFAULT_PITCH = 54.5`, 지금까지 실측한 사진들의 평균)으로 나머지를 외삽
  - **0개면** 기존처럼 `LabelsNotFoundError` → `roi.py`가 고정값으로 대체 (최후의 예비값은 유지)
- 검증: `board3.jpg`가 "10/15/20/25" 4개만으로 정확한 세로 범위를 계산해서, "30"(필기체라 OCR로는 못 읽은 라벨)까지 포함한 전체 행이 크롭 안에 제대로 들어옴. `basic_board.jpg`/`board1.jpg`/`board2.jpg` 세 장도 회귀 없이 그대로 정확함. 네 사진 다 `main.run_inference()`까지 정상 동작 확인
- 교훈: "필요한 조건 2개 중 하나가 없으면 전부 실패" 같은 설계는, 그 2개가 **서로 독립적으로 실패할 수 있는 이유**(여기선 서로 다른 라벨의 폰트 차이)가 있으면 특히 취약하다. 가진 정보(여기선 라벨 5개 중 일부)를 최대한 활용해서 등급을 낮춰가며(2개 이상 → 회귀, 1개 → 외삽, 0개 → 예비값) 대응하는 게 더 튼튼함

### Camo 출력 비율 검토

- 최신 Camo Studio의 프로필은 1:1 화면 비율을 지원함. 프로필 메뉴 또는 `Settings > Profiles`에서 1:1 프로필을 선택·생성할 수 있음.
- 1:1은 센서 원본을 그대로 보내는 의미가 아니라 보통 영상의 좌우를 잘라 정사각형 출력으로 만드는 것임. 따라서 검사 화질 개선책은 아님.
- 브레드보드 검사에서는 가능한 한 4:3 고해상도 원본을 받아 PC에서 필요한 ROI만 자르는 편이 정보 손실이 적음. 1:1은 촬영 범위가 정사각형으로 충분히 고정된 경우에만 사용.

### 1. 해상도만으로는 배율을 못 잡음 → `scale.py`

- 저해상도(720×720) 사진 실측: `scale.compute_scale`(해상도 비율)로 구한 배율이 0.2인데, 실제 홀 피치는 기준 사진과 거의 같았음(카메라가 훨씬 가까이서 찍어서 총 해상도는 낮아도 확대율은 높음). 해상도 기반 배율로 board_detect 상수들을 줄였더니 홀 검출 자체가 실패함.
- 해결: `label_detect.refine_y_range`가 OCR 라벨로 실측한 **진짜 행 피치**를 `_DEFAULT_PITCH`와 비교한 값을 `hole_scale`로 써서 `board_detect`에 넘김 (`roi.crop_to_roi`가 계산, 라벨을 못 찾은 경우에만 해상도 배율로 대체).

### 2. 카메라 방향이 사진마다 다름 → 4방향 탐색

- 새 사진들은 기존 90도 반시계 고정 회전이 안 맞음(레일이 가로로 누움). 방향을 고정하는 대신 **0/90/180/270도 네 방향을 다 시도**해서, 레일도 찾아지고 OCR 라벨도 읽히는 방향을 채택 (`roi._find_orientation`). OCR 성공 여부 자체가 방향 검증 수단 — 방향이 틀리면 숫자가 거꾸로/옆으로 찍혀 Tesseract가 거의 못 읽음.
- board4/5/6은 결과적으로 0도(회전 없음)가 정답으로 확인됨.
- OCR 인식률 개선도 필요했음: 이 카메라는 실제 홀 피치가 작아(글자도 작음) `_MIN_OCR_CONFIDENCE=80`이면 명백히 맞는 숫자도 신뢰도 0으로 다 걸러짐 → 0으로 낮춤(화이트리스트+정확한 라벨 문자열 일치라는 이중 필터가 이미 있어서 오탐 위험 적음). 추가로 OCR 전에 이미지를 확대(`_OCR_MIN_UPSCALE`)해서 인식률을 더 높임.

### 3. 열(컬럼) 검출: 부품에 가려 조각난 열 복구

- `board2.jpg`(IC칩 등으로 열 하나가 여러 조각으로 쪼개짐), `board5.jpg`(레일-단자부 사이 빈 공간에 노이즈가 13개나 뭉쳐서 15번째 "열"처럼 잡힘) 등 실측하며 `board_detect._fit_columns`를 여러 단계로 보강:
  1. 확실한 열들 사이 간격(피치)의 절반보다 가까운 조각들은 병합 (기존에도 있던 로직 유지)
  2. **개수가 넘치면**(15개 등) x폭이 가장 넓은 그룹부터 의심(진짜 열은 x폭 1~6px, 노이즈 뭉치는 20px+)스러운 걸로 보고 제외
  3. **개수가 모자라면**(13개 등) `_fill_missing_columns`로 빈 자리를 찾음 — 정상 구간 한가운데면 피치의 2배, 넓은 전환부 옆이면 "정상+넓은간격"(다른 넓은 간격들과 leave-one-out 비교로 진짜 넓은 것과 구분). **몇 개가 빈지 정확히 알고 있으므로(N_COLS-현재개수) 그만큼만 채우고 멈춤** — 안 그러면 애매한 나머지 간격이 계속 잘못 채워지는 무한 삽입 버그 생김(실측: board3.jpg 20개까지 채움).
  4. 산수 위치보다 **그 gap 안에 실제로 남아있는 조각(개수는 부족해도 위치는 실측값)이 있으면 그걸 우선 채택** — 렌즈 왜곡 때문에 산수 위치가 실제보다 15px 넘게 어긋날 수 있었음(board2.jpg IC 옆 열: 산수로는 438px인데 실제 조각은 453.7px에 있었고, IC 박스 안에 잘못 걸려서 "IC에 가려짐"으로 오탐했었음).
  - 시도했다가 버림: "그룹 x폭이 넓으면 무조건 재귀적으로 쪼갠다"는 방식(`_split_bridged_groups`)은 board5는 고쳤지만 board3을 다른 방식으로 망가뜨려서(진짜 열까지 과도하게 쪼갬) 되돌림. 지금은 "개수가 안 맞을 때만" 위 3/4번으로 대응.

### 4. 행(로우) 평면 왜곡: 레일 열이 짧게 잡히는 문제 → 라벨 기반 앵커로 전환 (가장 중요)

- **증상**: board4/5에서 A0/A13/U13 같은 모서리 좌표가 크게 어긋남 (`U13` y좌표가 크롭 이미지 높이(626px)보다 큰 630~640으로 계산됨). 사용자 확인: "한 행에 있는 핀홀들이 휘었다", "board4,5 hole들이 한 줄씩 내려왔어. 마지막 행은 hole이 잘림(매칭도 잘못됨). 첫 행은 True hole인데 안 찍혔고, 마지막행은 False hole인데 찍혔어."
- **원인**: `_fit_row_plane`이 "각 열의 마지막 검출점 = U행(마지막 행)"이라고 역산 추정하는데(`_assign_by_local_anchor`), **단자부 열(terminal)의 마지막 점이 사실 진짜 U행이 아니라 그 너머의 여분 점**이었음 — 반대로 **레일 열의 마지막 점이 진짜 U행**이었음(OCR로 독립 실측한 행 위치와 비교해서 확인). 단자부 열 개수(10개)가 레일(4개)보다 많아서 1차 피팅이 "틀린 단자부 가정" 쪽으로 쏠려, 전체 평면의 x기울기(coef2)가 왜곡되고 결과적으로 모든 행 인덱스가 한 칸씩 밀림.
  - 처음엔 "레일 열만 신뢰 안 함" + "실제 개수가 기대치보다 너무 적은 열도 신뢰 안 함"(`_TRUSTED_COL_SLACK`)으로 1차 피팅에서 제외하는 방식으로 고쳤는데, board4/5 코너는 정상화됐지만(A0≈A13, U0≈U13, 이미지 높이 안에 들어옴) 사용자가 재확인해보니 여전히 마지막 행 근처가 미묘하게 안 맞았음.
  - 크롭 여백(`_ROW_MARGIN_RATIO`)을 0.75→1.2로 키워서 레일의 마지막 홀을 더 확실히 담아보려 했으나, board3.jpg에서 **위아래 인접 보드 유닛의 내용까지 크롭에 딸려 들어와서** YOLO가 잘린 부품을 추가로 오탐하는 회귀가 생겨 되돌림(0.75 유지).
- **최종 해결 (사용자 제안)**: "10~30 라벨 옆 hole을 기준점으로 쓰면 되지 않냐"는 제안 채택. OCR로 이미 찾아둔 "10"/"15"/"20"/"25"/"30" 라벨의 **실제 (x, y) 위치 자체**를 행 평면의 1차 피팅 앵커로 직접 사용 — 어떤 열의 점 개수나 끝점 위치에도 의존하지 않는, 훨씬 신뢰도 높은 관측값이기 때문.
  - `label_detect.find_label_row_points`가 라벨의 x좌표도 같이 반환하도록 수정 (기존엔 y만 반환).
  - `label_detect.refine_y_range`가 `(y1, y2, pitch)`에 더해 **원본 라벨 앵커 목록(행번호, x, y)**도 반환.
  - `roi.crop_to_roi`가 이 앵커를 크롭 후 좌표계로 옮겨서(`x1,y1`만큼 빼기) `(크롭이미지, 배율, 라벨앵커)` 3-튜플로 반환하도록 시그니처 변경. `main.py`, `dev_plot_infer.py`, `board.all_holes_from_image`, `board_detect.find_pinhole_pixels`까지 전부 관통해서 전달.
  - `board_detect._fit_row_plane`: 라벨 앵커가 3개 이상이고 x좌표가 충분히 퍼져 있으면(피치*3 이상) **그 앵커만으로 1차 평면을 직접 피팅**. 그 평면으로 재배정했을 때 열마다 최소 3개 이상 유효 범위에 들어오는지 sanity check — 이상하면 버리고 **기존 "신뢰 열" 방식으로 자동 폴백** (사용자 요청: "안되면 다시 원래방식으로 돌아오게"). 1차 피팅 방식이 뭐였든, 그 평면으로 전체 열을 재배정 후 재피팅하는 2차 과정은 동일.
  - **결과**: board4 코너 — A0=(26.2, 26.2), A13=(562.0, 24.4), U0=(26.2, 599.1), U13=(562.0, 597.3). board5 — A0=(25.0, 25.1), A13=(533.7, 24.6), U0=(25.0, 569.7), U13=(533.7, 569.2). 이전엔 최대 30px대로 벌어지던 좌우 기울기가 1~2px 수준으로 줄어듦. board0~6 전부 회귀 없이 재검증 완료.

### 5. board2.jpg IC칩 옆 열(10,11번) 위치 여전히 부정확 → 확실한 열 기준 균등 재배치

- 사용자 재확인: "board2 오른쪽 부분 열 위치 안 맞아. 갑자기 행 간격 늘어나는 것도 이상하잖아. 핀홀 사이의 간격 계산해서 그거대로 채우면 되는 거 아님? 일부 핀홀들은 제대로 보이니까 그걸로 검증하고."
- 확인: col10(x≈411)이 실제로는 IC 다리에 가려 조각난 여러 그룹이 억지로 병합된 것 — 원본 x값들이 396~426px 사이에 **고르게 퍼져있어서**(한두 개 튄 값이 아니라 전체적으로 분산됨) 병합 후 대표 x가 실제 위치에서 크게 벗어남.
- **해결**: "확실한 열"과 "애매한 열"을 구분해서, 애매한 열이 확실한 두 열 사이에 있으면 그 자리 좌표를 버리고 **확실한 두 열 사이 간격을 피치대로 균등 재배치**한다(`_respace_unconfident_columns`) — 사용자가 제안한 "핀홀 간격 계산해서 채우기"를 그대로 구현.
  - 확실함 판정 기준을 처음엔 x폭(최대-최소)으로 했는데, `board1.jpg`에서 회귀 발생: 노이즈로 튄 점 1~2개만 있어도(나머지는 멀쩡한데) x폭이 12~21px까지 벌어져서 멀쩡한 열 6개가 잘못 "애매함"으로 분류되고 엉뚱하게 재배치되어 커버리지가 18→15로 줄어듦.
  - **IQR(25~75퍼센타일 폭)로 교체**해서 해결: 소수 이상치에 안 흔들리는 통계량이라, board1의 멀쩡한 열들은 전부 IQR≤2.8인데 board2의 진짜 문제 열(x=411)은 IQR=24.8로 뚜렷하게 구분됨.
  - 구현 중 버그 하나 더 발견: 열 개수가 부족해서 `_fill_missing_columns`를 거치면, 그 뒤에 confident 배열을 "원래 있던 x였는지" 기준으로 통째로 다시 계산했는데, 이러면 **원래 있었지만 애매하다고 판정했던 열**(예: 위 x=411)도 "원래 있었다"는 이유로 확실함으로 잘못 재분류됨. 원래 계산해둔 confident 값을 `dict`로 보존해서 필드 채우기 이후에도 유지하도록 수정.
- 결과: board2 col10=411.1→416.4, col11=(신규 채움 위치)→458.3로 재배치. IC 다리(col10 바로 왼쪽, 실측으로 검증된 노란 점들)와의 간격이 다른 정상 열 간격과 일치. board0~6 전체 회귀 없음 재확인.

### 6. `_respace_unconfident_columns`가 구간(레일/단자부) 경계를 몰라서 채널 간격까지 뭉갬

- 사용자 재확인("야 다시 해봐 버그있는지 지금 안 맞는게 있어")으로 board2를 다시 실측해보니, 바로 위 5번 수정이 **또 다른 문제**를 만들어냈음을 발견.
- **증상**: col9(x=374.5, 확실)~col12(x=500.26, 확실) 사이를 균등 3등분해서 col10=416.4, col11=458.3이 나왔는데, 실측해보면 이 값들은 **간격 41.9px씩 균등** — 그런데 col12는 레일 열(col12,13)이고 col9~col11은 단자부 열(col7~11)이라, 원래 col11↔col12 사이엔 훨씬 넓은 채널(~75px)이 있어야 하고 col9↔10↔11은 정상 피치(~27~29px)여야 함. 즉 `_respace_unconfident_columns`가 "확실한 열"이라는 판정만 보고, 그 확실한 두 열이 **서로 다른 물리적 구간(레일/단자부)**에 있다는 걸 몰라서 균등 재배치를 잘못 적용함.
- **원인**: 열 배치는 `[레일 2열][단자부 5열][채널][단자부 5열][레일 2열]` 순서라 구간 경계(1↔2, 6↔7, 11↔12)의 간격이 구간 내부 정상 피치의 약 3배임(`_fill_missing_columns`는 이미 이걸 알고 있었지만, `_respace_unconfident_columns`는 몰랐음).
- **해결** (`board_detect.py`):
  - 열 인덱스 → 구간(0/1/2/3) 매핑용 상수 `_COL_SEGMENTS = [(0,1),(2,6),(7,11),(12,13)]`과 헬퍼 `_col_segment_id` 추가.
  - `_respace_unconfident_columns`가 확실하지 않은 열들의 run을 **구간 경계 단위로 쪼개서** 처리하도록 재작성. 같은 구간 안에 양쪽 다 확실한 열이 있으면 기존처럼 균등 재배치. **한쪽만** 있으면(반대쪽 확실한 열이 다른 구간에 있어서 못 씀) — 확실한 열들끼리 같은 구간 안에서 측정한 "정상 피치"(`_estimate_normal_col_pitch`, 구간 경계 간격은 제외하고 계산)로 그 방향으로 뻗어서 채움. 둘 다 없으면 원래 위치 유지.
- **검증**: board2 col9→10→11 간격이 26.94/26.94로 정상 피치와 일치, col11→12 간격이 71.89로 다른 채널 간격(78.37, 80.53 등)과 비슷한 크기로 복원됨. 확대 이미지로 col10·col11이 IC칩 오른쪽 다리·물리적 홀과 정확히 겹치는 것도 확인. 커버리지 43→52로 증가(이전엔 안 맞는 위치 때문에 IC 박스 판정이 틀렸던 홀들이 이제 올바르게 매칭됨). board0~6 전 구간 재검증: 정상 피치 25~30px, 채널 간격 71~86px로 전부 일관됨, 나머지 보드는 커버리지 개수 그대로(회귀 없음).
- 교훈: "확실한 두 값 사이는 균등하게 나누면 된다"는 보정은, 그 사이에 **알려진 비균등 구조(여기선 레일↔단자부 채널)**가 있으면 오히려 새로운 왜곡을 만든다. 이미 알고 있는 물리적 구조(구간 경계)를 보정 로직에도 명시적으로 반영해야 안전함.

- **중요한 한계**: 이 비교는 라벨 없는 육안 확인 3장짜리라, "8n이 객관적으로 낫다"고 단정할 근거는 아님 — 각 모델이 이 테스트 사진들을 학습에 썼는지(데이터 오염) 여부도 확인 안 됨. 제대로 하려면 어느 모델도 학습에 안 쓴 held-out 검증셋 + 정량 지표가 필요함.

### 핀홀 매칭을 "박스 안 전부"에서 "실제 다리 위치"로 전환

- 사용자 요청 배경: station(C#)에 넘길 핀홀 정보가 "박스에 걸친 홀 전부"라서, 부품 몸통이 여러 홀에 걸쳐 보이면 실제로 다리가 없는 자리까지 장착으로 잘못 보고되는 문제가 있었음(예: IC칩 하나가 24개 홀을 장착으로 보고 — 실제 다리는 14개뿐).
- [board.py](app/board.py) `match_holes_to_boxes` 재작성, 부품 종류별 규칙 도입:
  - `led`/`capacitor`(다리 2개): 기존 로직 유지 — 박스 중심에서 가장 가까운 2개
  - `black_wire`/`red_wire`/`white_wire`/`resistance330`/`resistance470`(다리 2개, 몸통 양 끝): 박스의 긴 축 방향으로 정렬해서 **양 끝 2개**만 인정. 처음엔 저항을 이 규칙에서 빼놨었는데(무전선만 우선 적용), 사용자가 "wire, resistance 규칙: 다리 2개 가장 바깥쪽"이라고 명시적으로 재확인해서 저항도 포함시킴 — board1에서 저항 3개가 전부 가운데 홀까지 3개씩 잘못 찍혀 있던 게 이 수정으로 정확히 양 끝 2개로 줄어듦
  - `ic_chip`(다리 14개): 처음엔 "박스 중심에서 가까운 14개"만 했더니, 중간 열(몸통에 가려진 빈 홀)이 실제 다리보다 중심에 더 가까울 수 있어서 엉뚱한 홀이 선택될 위험이 있었음 → 사용자 지적으로 **먼저 후보를 바깥쪽 두 열(테두리)로 좁힌 다음** 그중 중심에서 가까운 14개를 고르도록 2단계로 수정
- 검증: `new_test_images/board0~6` 7장 전부 `dev_plot_infer.py`로 오버레이 재생성(초록=빈 홀, 노랑=다리 꽂힌 홀). board0(빈 보드)은 전부 초록, 나머지는 부품별 정확한 다리 개수만큼만 노란 점으로 찍힘을 확인. 실제 서비스가 참조하는 `new_test_images/board*_infer.jpg`도 최신 로직으로 덮어씀(이 파일들은 9/23 예전 로직으로 만들어져 있어서 사용자가 확인하다가 "지금 wire랑 resistance 노란 점이 4개야"라고 지적 — 옛날 파일을 보고 있었던 것으로 확인됨).

### 같은 부품의 중복 박스 탐지 제거 (`_deduplicate_boxes`)

- 위 "다리 위치" 로직이 **박스 단위**로 동작하다 보니, YOLO가 부품 하나를 박스 여러 개로 중복 탐지하면 박스마다 따로 다리를 채워서 실제보다 홀이 더 많이 장착된 것처럼 나오는 문제가 새로 드러남 (`board4.jpg`의 IC칩 하나가 신뢰도 0.96/0.28 박스 2개로 잡혀서, 14개씩 두 번 채워지며 사실상 원래의 24개 전부가 다시 채워짐).
- [main.py](app/main.py)에 `_deduplicate_boxes` 추가: 신뢰도 높은 순으로 정렬해서, 겹침 비율(IoU) 0.5 이상인 박스는 뒤에 나온(신뢰도 낮은) 것을 버림. 처음엔 "같은 클래스일 때만" 중복으로 봤음(다른 부품끼리 겹치는 건 정상이라는 가정).
- **클래스가 다른 중복도 실측으로 발견**: 사용자가 "board4의 C10/F10, D10/E10은 같은 저항이야"라고 지적 — 확인해보니 정말 거의 같은 위치(x1≈419.5/419.3, y1≈69.4/70.3 등)에 박스 2개가 있는데 하나는 `resistance470`(0.70), 하나는 `resistance330`(0.47)으로 **클래스까지 다르게** 잡혀 있었음. "같은 클래스일 때만" 조건 때문에 이 케이스를 놓쳐서, 저항 하나가 서로 다른 값의 저항 2개인 것처럼 보고되고 있었음.
- 사용자 확인("중복 검출은 신뢰도 높은 걸로 판단하라고 한 거야")에 따라 클래스 조건을 제거 — **겹침 비율만으로** 중복 판단(실제 부품은 한 자리에 하나뿐이므로, 위치가 거의 같으면 클래스를 다르게 헷갈렸어도 같은 물체로 봄). 검증: board4에서 D10/E10을 만들던 낮은 신뢰도 박스가 사라지고 C10/F10(진짜 저항)만 남음.

### API 계약 문서(`docs/api-contract.md`) 갱신

- 응답 예시의 `class` 값이 실제 학습된 클래스명과 다른 낡은 값(`"resistor_220"`)이었던 것을 실제 8종(`black_wire`/`capacitor`/`ic_chip`/`led`/`red_wire`/`resistance330`/`resistance470`/`white_wire`)으로 갱신.
- "부품당 다리 개수만큼 배열 원소가 나뉘어 나온다"는 설명 추가 — 사용자가 "class별로 pinhole정보 주는게 아니야?"라고 질문해서, 지금 계약은 클래스로 그룹핑한 구조가 아니라 계속 평평한(flat) `{pinhole, class, confidence}` 배열이었음을 확인·재확인. 사용자가 기존 형식 유지하기로 결정(station 쪽에서 필요하면 클래스별로 묶어서 쓰기로 함).
